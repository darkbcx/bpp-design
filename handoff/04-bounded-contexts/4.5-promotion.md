# 4.5 Promotion

The Promotion context owns **vouchers and voucher usage**. It's a small, focused context — store-scoped vouchers in v1, with no platform-wide promotions and no rule engine.

> Backed by: [ADR-0007](../../decisions/0007-pricing-tax-and-vouchers.md) (vouchers); [ADR-0008](../../decisions/0008-localization-and-localizedtext.md) (`Voucher.description` is `LocalizedText`); [ADR-0017](../../decisions/0017-order-and-fulfillment.md) (Order applies and reverts vouchers).
> No separate sub-design doc — the ADR is the full reference.

## Position and ownership

**Owns:**
- `Voucher` — the code-based promotion definition.
- `VoucherUsage` — the authoritative redemption log; enforces usage limits.

**Cross-context references** (by ID only):
- `Store.id` — vouchers are store-scoped.
- `User.id` — recorded in `VoucherUsage` for per-user limit enforcement.
- `Order.id` — recorded in `VoucherUsage` to link the redemption to the order.

**Is consumed by:**
- **Order & Fulfillment** — the only context that applies and reverts vouchers, via the Promotion application layer.
- **Audit** — subscribes to all Promotion events.

## Key concepts

### Voucher

| Field | Description |
|---|---|
| `id` | Internal opaque |
| `store_id` | Owning Store |
| `code` | Case-insensitive; **unique within store** |
| `description` | `LocalizedText` (per [ADR-0008](../../decisions/0008-localization-and-localizedtext.md)) |
| `discount_type` | `percentage` \| `fixed_amount` |
| `discount_value` | Decimal (percentage) or `Money` (fixed) |
| `max_total_uses` | Integer; optional (null = unlimited) |
| `max_uses_per_user` | Integer; optional |
| `starts_at`, `expires_at` | Optional validity window |
| `minimum_cart_value` | `Money`; optional |
| `status` | `Active` \| `Disabled` (owner toggle) |
| `current_total_uses` | Derived from `VoucherUsage` count; cached for fast limit checks |

**Derived states** (not stored):
- `Expired` — `expires_at < now`
- `Exhausted` — `current_total_uses >= max_total_uses`

A voucher is **usable** if all of: `status == Active`, not Expired, not Exhausted, and `now >= starts_at`.

### VoucherUsage

| Field | Description |
|---|---|
| `id` | Internal opaque |
| `voucher_id` | Reference |
| `user_id` | The Beckn buyer's mapped user reference; nullable (since buyers are not Users — see notes below) |
| `order_id` | Order reference |
| `applied_at` | Timestamp |
| `discount_applied_amount` | `Money`; actual discount computed at quote time |

`VoucherUsage` is the **authoritative redemption log**. Per-user limits are enforced by counting matching rows.

## Discount × tax interaction

Voucher discount applies to the **pre-tax `base_price`** (per [ADR-0007](../../decisions/0007-pricing-tax-and-vouchers.md)); tax is then recomputed on the discounted base. This is GST/VAT-compliant — tax accrues on the actual receivable, not the list price.

## Application and rollback flow

The Order context drives all voucher interaction:

1. **At quote time** (`/select` or first-party checkout):
   `Order.CreateQuote` → `Promotion.ValidateVoucher(code, store, user, cart_total)` → returns computed discount or typed error.

2. **At order confirm** (`/confirm`):
   `Order.Confirm` → `Promotion.RecordVoucherUsage(voucher, user, order, applied_amount)` → emits `promotion.voucher_redeemed`; bumps `current_total_uses`.

3. **At order cancel post-Confirm** (per [ADR-0017](../../decisions/0017-order-and-fulfillment.md)):
   `Order.Cancel` → `Promotion.RevertVoucherUsage(voucher_usage_id, reason)` → emits `promotion.voucher_usage_reverted`; the usage no longer counts against limits.

The Promotion context does **not** mutate the Order. It just provides the validation and the usage log.

## Lifecycles

### Voucher

- (new) → `Active` (created by Store Admin / Org Owner)
- `Active` → `Disabled` (owner toggle); `Disabled` → `Active`
- No deletion (per [§2.8](../02-principles.md))
- `Expired` and `Exhausted` are derived states (read-time computation).

### VoucherUsage

- (new) → recorded at `Promotion.RecordVoucherUsage`
- Optional revert flag set on `Promotion.RevertVoucherUsage` (the row stays; usage count decrements accordingly)

## Boundary contracts (highlights)

### Use cases exposed

**Store-scoped (Org Owner / Store Admin):**
- `CreateVoucher`, `UpdateVoucher`, `DisableVoucher`, `EnableVoucher`
- `ListVouchers`, `GetVoucherDetail`, `GetVoucherUsageHistory`

**Called by Order context (cross-context):**
- `ValidateVoucher(code, store, user, cart) → ValidatedDiscount | TypedError`
- `RecordVoucherUsage(voucher, user, order, applied_amount) → VoucherUsage`
- `RevertVoucherUsage(voucher_usage_id, reason)`

### Domain events emitted

`promotion.voucher_created`, `promotion.voucher_updated`, `promotion.voucher_disabled`, `promotion.voucher_enabled`, `promotion.voucher_redeemed`, `promotion.voucher_usage_reverted`.

Full registry: [`design/events.md`](../../design/events.md).

## Notable rules

- **Store-scoped only in v1.** No platform-wide vouchers. Each store creates its own.
- **One voucher per order** in v1. No stacking; no combining percentage + fixed-amount.
- **Discount applies to `base_price`**, not `published_price`. Tax recomputes on the discounted base.
- **Voucher application is Order-mediated.** The Promotion context never modifies an Order; the Order context owns Quote construction and cancellation.
- **`VoucherUsage` is the source of truth** for usage limits; the `current_total_uses` field on Voucher is a cache derived from it.
- **Per-user limits depend on `user_id`** being present in `VoucherUsage`. With buyers-not-Users (per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)), the `user_id` reference in `VoucherUsage` is the Beckn buyer's mapped identifier (BAP-supplied) — operational specifics are part of the Order context.

## Out of scope (v1)

- **Platform-wide promotions** — would introduce a `platform_id` discriminator. Future.
- **Rule-based promotions** — BOGO, X-for-Y, automatic cart discounts. Future.
- **Customer-specific pricing tiers** (B2B, members, loyalty). Future.
- **Voucher stacking** (multiple per order). Default rule is one per order.
- **Time-bound list-price changes** (sales windows on catalog prices). Vouchers approximate this; direct sale-pricing would be a separate feature.
- **Voucher distribution mechanics** (sharing codes via email, links). Operational; not domain.
