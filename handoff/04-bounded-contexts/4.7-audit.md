# 4.7 Audit

The Audit context is **the system's tamper-evident history of state changes**. It is a downstream subscriber of the domain event stream — every mutation event from every context becomes an `AuditRecord` with longer retention than the event log itself.

> Backed by: [ADR-0014](../../decisions/0014-soft-delete-and-audit.md) (Audit context; soft-delete pattern), [ADR-0011](../../decisions/0011-domain-events.md) (event substrate Audit subscribes to), [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md) (PII scrubbing in audit records), [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md) (actor + impersonator attribution).
> Full entity model and access matrix: [`design/audit.md`](../../design/audit.md).

## Position and ownership

**Owns:**
- `AuditRecord` — one per consumed domain event. Append-only.

**Cross-context references** (by ID only):
- `User.id` — actor (and impersonator, if applicable) on every audit record.
- `aggregate_id` — opaque reference to whatever aggregate the source event was about (Store, Product, Order, etc.).

**Subscribes to:**
- The domain event stream (per [ADR-0011](../../decisions/0011-domain-events.md)) — broad subscription across all contexts; specific noise events excluded via config.

**Is consumed by:**
- **System Admin** — platform-wide history (incidents, compliance, debugging).
- **Platform-scoped operators** with the `audit.read.platform` capability.
- **Store Owners / Org Owners / Store Admins** — records pertaining to their stores.
- **Users** — their own activity history (including impersonation events where they were the real actor or the impersonated party).
- **External auditors** — via System-Admin-mediated reports.

**Emits no events.** Audit is a sink, not a source. Downstream consumers (analytics, alerting, etc.) subscribe to the original event stream, not to Audit.

## Key concept: AuditRecord

One row per consumed event. Immutable once written.

| Field | Description |
|---|---|
| `audit_id` | Opaque internal identifier |
| `event_id` | From source event (dedup key per ADR-0011) |
| `event_name` | E.g., `tenancy.store_status_changed` |
| `event_version` | From source event |
| `recorded_at` | When Audit ingested the event |
| `occurred_at` | From source event |
| `actor` | `{ user_id, impersonated_user_id, active_org_id, active_store_id }` — per [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md) + [ADR-0018](../../decisions/0018-organization-tenancy.md) |
| `aggregate_type` | E.g., `Store`, `Product`, `Order`, `User` |
| `aggregate_id` | Identifier of the affected aggregate |
| `before_state` | Optional; for change events with a previous state |
| `after_state` | Optional; for change events with a new state |
| `summary` | Human-readable rendering of the event |
| `correlation_id` | For tracing across events from one operation |
| `source_envelope` | Full original event envelope (archival snapshot) |

`source_envelope` preserves the original event even if the event schema evolves.

## Subscription scope

Audit subscribes to **all mutation events** across all contexts. The default posture is "audit everything that changes state." Configurable per-event-name exclusions handle noise (e.g., `identity.session_active_store_set` is high-volume and low-information).

Audit deduplicates by `event_id` via the standard inbox pattern (per [ADR-0012](../../decisions/0012-cross-context-consistency.md)).

## Lifecycle

`AuditRecord`s are immutable once written. The only state transition is **expiry-and-deletion**, driven by the retention policy and performed by a privileged cleanup role with row-level scope.

## Access matrix (per [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md) + [ADR-0016](../../decisions/0016-authorization-details.md))

| Reader | Records visible |
|---|---|
| **System Admin** | All — platform-wide read |
| **Platform-scoped** with `audit.read.platform` | All (or subset per finer capability) |
| **Org Owner / Store Admin** | Records where `aggregate_type` belongs to a store in their Org, OR `actor.active_org_id` is their Org |
| **User** | Records where `actor.user_id == self.id` OR `actor.impersonated_user_id == self.id` |
| **(Beckn buyers)** | Not applicable — buyers are not Users; they cannot read audit |

Authorization checks happen in the Application Layer of Audit; read use cases enforce the filter before returning records.

## Retention (per record category)

Configurable per `event_name` (or category). Defaults:

| Category | Default retention |
|---|---|
| Financial / Order / Voucher redemption events | **~7 years** |
| Inventory adjustments | ~3 years |
| Business state changes (Store, Product, Membership lifecycle) | ~2 years |
| Identity & Session events | ~1 year |
| Catalog-routine events (media updates, etc.) | ~1 year |

Specific values are tunable by compliance / Gap 17 / [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md).

## Tamper resistance — DB role separation

- **`audit_subscriber`** — `INSERT` only on `audit_records`. No `UPDATE`, no `DELETE`.
- **`audit_pii_scrubber`** (per [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md)) — field-level `UPDATE` on `source_envelope` only, when right-to-erasure is processed. All other audit fields remain read-only.
- **`audit_cleanup`** — `DELETE` only on `audit_records`, with row-level filter (`recorded_at + retention < now()`).
- **`audit_reader`** — `SELECT` only; respects the access matrix above.

No role has `UPDATE` on any field other than `source_envelope`. Records cannot be modified post-write.

**Cryptographic chaining** (each record references the hash of the prior) is **deferred** to a future ADR if compliance demands; not in v1.

## PII handling in audit

`AuditRecord.source_envelope` can carry snapshot PII (e.g., the user's email at sign-in, the buyer's contact details at order init). Per [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md):

- The PII catalog in `design/pii.md` declares which fields in each event payload are PII.
- On right-to-erasure (`ScrubUser`), the dedicated `audit_pii_scrubber` walks affected records and replaces PII fields in `source_envelope` per the catalog's scrub-action types.
- The audit record itself stays — only PII fields are scrubbed in place. This honors the no-delete invariant *and* the right to erasure.

## Boundary contracts (highlights)

### Use cases exposed

**Internal (subscriber-driven):**
- `IngestEvent(event)` — invoked by the dispatcher; idempotent by `event_id`; transforms event into AuditRecord and writes.

**Read-side (capability-gated):**
- `GetAuditRecord(audit_id, acting_user) → AuditRecord | NotAllowed | NotFound`
- `ListRecordsForStore(store_id, filter, acting_user) → [AuditRecord]`
- `ListRecordsForUser(user_id, filter, acting_user) → [AuditRecord]`
- `SearchRecords(query, filter, acting_user) → [AuditRecord]` — platform-scope.

Full list in [`design/audit.md`](../../design/audit.md).

### Domain events

**None.** Audit is a sink.

## Notable rules

- **One AuditRecord per consumed event.** No higher-level "audit operations" composition in v1.
- **Append-only at the DB role level.** Tamper resistance is enforced by permissions, not by code convention.
- **`source_envelope` is the archival snapshot.** Subscribers reading old records may see old event versions; tooling tolerates this.
- **Audit is not the event log.** Decoupled from `outbox` retention; audit keeps records per its own (longer) compliance windows.
- **Access is capability-gated**, with row-level filters layered on top per the access matrix above.
- **PII scrubbing is the only permitted update.** No other field can be modified.

## Out of scope (v1)

- **Cryptographic chaining** (tamper evidence beyond append-only roles) — deferred.
- **Higher-level audit operations** (events grouped into business operations as a derived read view) — future enhancement.
- **Cross-tenant audit summarization** — analytics surface, not Audit's scope.
- **Audit search / query UX** — Interface Layer concern.
- **External SIEM / log shipping** — operational concern; can be added without changing Audit's domain.
