# 4.1 Identity & Access

The Identity & Access context owns **User identity** and **Sessions**. The platform delegates authentication entirely to an external **Identity Provider (IdP)** via OpenID Connect (OIDC); this context mirrors the User profile from the IdP, manages the platform's own session model, and provides the actor-resolution port that every other context uses for authorization.

> Backed by: [ADR-0009](../../decisions/0009-identity-and-external-idp.md) (IdP integration), [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md) (active session attributes), [ADR-0018](../../decisions/0018-organization-tenancy.md) (active Org), [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md) (User scope).
> Full entity model and sequence diagrams: [`design/identity.md`](../../design/identity.md).

## Position and ownership

**Owns:**
- The `User` entity — mirrored from the IdP via OIDC.
- The `Session` entity — opaque-token session, independent of the IdP's token.

**Is consumed by:**
- **Tenancy** — references `User.id` from `OrganizationMember` and `StoreAdminAssignment`.
- **Audit** — actor attribution (`User.id` + impersonator).
- **All contexts** — via the `AuthorizationPort` for capability checks (per [§5.1](../05-cross-cutting.md), forthcoming).
- **Beckn Bridge** — uses `ResolveActorFromSession` for Admin-UI-initiated calls; the Bridge does NOT project User data to Beckn (Beckn buyers are not Users — see [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)).

**Outbound cross-context calls:** none. Identity is a source, not a consumer.

## User scope (per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md))

The `User` entity is exclusively for **tenant-side and platform-side actors**:
- Org Owners
- Org Members (including those promoted to Store Admin)
- System Admins
- Platform-scoped operators

**Buyers are never Users.** They arrive via BAPs over the Beckn network and are captured per-order with Beckn buyer references in the Order context — they have no User account, no IdP identity in our system.

## Key concepts

### User

Two-tier profile model:

- **IdP-canonical** (refreshed from the IdP on every sign-in; read-only in-app): `email`, `email_verified_at`, `display_name`.
- **Platform-owned** (initial mirror from IdP at first sign-in; mutable in-app thereafter): `preferred_locale`, `avatar_url`.
- **System-managed**: `id` (internal opaque, the cross-context reference key), `external_subject_id` (IdP `sub`, immutable, unique), `status` (`Active` | `Disabled`), timestamps.

The platform does not store passwords, MFA secrets, or recovery tokens — all of that lives at the IdP.

### Session

Platform-issued opaque-token session attached to a User. Independent of the IdP token (the IdP token is exchanged for a Session at sign-in and not retained).

Carries:
- `user_id`
- `active_org_id` (nullable — required for tenant-scoped actions; null only for System Admin / platform-scoped users in their no-tenant mode)
- `active_store_id` (nullable — when set, must belong to the active Org)
- `device_label`, `last_ip`
- `created_at`, `last_used_at`, `expires_at`

Idle lifetime: 30 days default (operational config). Operations: sign-out (one), sign-out-everywhere (all sessions for a user).

## Lifecycles

### User lifecycle

| From → To | Trigger |
|---|---|
| (new) → Active | Just-in-Time provisioning at first successful IdP sign-in. No separate sign-up endpoint. |
| Active → Disabled | System Admin / platform-scoped action |
| Disabled → Active | System Admin / platform-scoped action |

No deletion (per [§2.8](../02-principles.md)). Right-to-erasure is **PII scrubbing in place** — see [§5.6 PII handling](../05-cross-cutting.md) (forthcoming) and [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md).

### Session lifecycle

States are implicit — a Session exists (active) or doesn't.

- **Create** at successful sign-in.
- **Refresh** `last_used_at` on each authenticated request.
- **Set / clear** `active_org_id` and `active_store_id` via UI switchers.
- **End** via sign-out (one) or sign-out-everywhere.
- **Expire** lazily when `last_used_at + idle_window < now`.

When a User is **Disabled**, all their active Sessions are terminated.

## Sign-in flow (JIT provisioning)

```
1. Visitor → GET /auth/start
2. App generates state + nonce; redirects to IdP authorization endpoint
3. IdP authenticates (sign-up at IdP if first time; sign-in if returning)
4. IdP → GET /auth/callback?code&state
5. App validates state, exchanges code at IdP token endpoint
6. App validates id_token (signature via JWKS, issuer, audience, expiry, nonce)
7. Lookup User by external_subject_id
   • If found: refresh IdP-canonical fields; check status != Disabled
   • If not found: create User (JIT) with mirrored fields; status = Active
8. Create Session; set HTTP-only cookie
9. Redirect to original destination
```

Detailed steps and the security checks at each step are in [`design/identity.md`](../../design/identity.md) §"Sign-in flow".

## Profile sync rules

On every successful sign-in:
- Refresh **IdP-canonical** fields (`email`, `email_verified_at`, `display_name`) from current claims.
- Do **NOT** touch **platform-owned** fields (`preferred_locale`, `avatar_url`).
- Update `last_signed_in_at`, `last_profile_synced_at`.
- If a refresh would create an `email` collision with another User → reject the sign-in with a typed error (rare edge case).

## Boundary contracts (highlights)

### Use cases exposed (Application Layer)

- **Sign-in / out**: `BeginSignIn`, `CompleteSignIn`, `SignOut`, `SignOutEverywhere`
- **Session**: `RefreshSessionActivity`, `SetActiveOrg`, `SetActiveStore`, `ClearActiveOrg`, `ClearActiveStore`
- **Profile** (platform-owned fields): `UpdatePreferredLocale`, `UpdateAvatarUrl`
- **Admin actions** (capability-gated): `DisableUser`, `ReactivateUser`
- **Read-side**: `GetUserById`, `GetUserByEmail`, `ResolveActorFromSession`, `ListSessionsForUser`

Full list in [`design/identity.md`](../../design/identity.md) §"Boundary contracts".

### Domain events emitted

`identity.user_created`, `identity.user_signed_in`, `identity.user_profile_synced`, `identity.user_preferred_locale_changed`, `identity.user_avatar_changed`, `identity.user_disabled`, `identity.user_reactivated`, `identity.session_created`, `identity.session_ended`, `identity.session_active_store_set`, `identity.session_active_store_cleared`, `identity.authorization_denied`, `identity.user_pii_scrubbed`.

Full registry: [`design/events.md`](../../design/events.md).

### How other contexts authenticate requests

Every authenticated request from any first-party interface carries the Session cookie. The Application Layer of any context calls:

```
ResolveActorFromSession(session_id) → { user_id, active_org_id, active_store_id, status }
```

If null or `status == Disabled`, the request is rejected. Otherwise authorization continues with `requireCapability(...)` (per [§5.1](../05-cross-cutting.md), forthcoming).

## Notable rules

- **`User.id` is the cross-context reference key.** Not `external_subject_id`, not `email`.
- **`email_verified_at` is trusted from the IdP.** Action gates (creating a store, accepting an invitation, etc.) check this attribute.
- **IdP-canonical fields are read-only in-app.** Users change them at the IdP.
- **Platform-owned fields are mutable in-app.** `preferred_locale` and `avatar_url` are mirrored only at first creation, then owned locally.
- **One `external_subject_id` per User in v1.** Multi-IdP linking is deferred.
- **Buyers are not Users** (per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)) — the IdP integration is for admin/platform actors only.

## Out of scope (v1)

- **Multi-IdP linking** (one external identity per User).
- **In-app push of profile edits to IdP** (one-way: IdP → us).
- **MFA enforcement requirements** — operational, at the IdP layer.
- **Anonymous / guest checkout** — no first-party buyer flow at all per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md).
- **Account locking for suspicious activity** — operational.
- **IdP-side webhook integration** (e.g., notify on IdP-side user delete) — operational, future.
