# 4.3 Catalog

The Catalog context owns **what a store sells** — Products (with optional Variants), their attributes, media, categorization, pricing, and the named **Catalogs** that group them. It's the largest context by surface area and the primary input to Beckn projection.

> Backed by: [ADR-0004](../../decisions/0004-store-publication-and-multi-catalog-projection.md) (multi-catalog projection), [ADR-0005](../../decisions/0005-catalog-and-product-modeling.md) (Product modeling), [ADR-0007](../../decisions/0007-pricing-tax-and-vouchers.md) (pricing and tax), [ADR-0008](../../decisions/0008-localization-and-localizedtext.md) (LocalizedText), [ADR-0020](../../decisions/0020-default-catalog-mandatory.md) (Default Catalog mandatory).
> Full entity model: [`design/catalog.md`](../../design/catalog.md).

## Position and ownership

**Owns:**
- `Product` (and its `Variant`s in Matrix mode)
- `ProductAttribute` (variant-defining attributes; Matrix mode only)
- `Catalog` (the **Default Catalog** and zero-or-more **additional Catalogs** per store)
- `CatalogMembership` (additional Catalogs only; Default is implicit)
- `PlatformCategory` (hierarchical taxonomy, platform-defined)
- `ProductCategoryAssignment`, `Media`

**Cross-context references** (by ID only):
- `Store.id` — every Product / Catalog belongs to exactly one Store.
- `User.id` — only in events (actor attribution).

**Is consumed by:**
- **Inventory** — references `Product.id` (Flat) or `ProductVariant.id` (Matrix) for `StockLevel`.
- **Promotion** — Voucher application happens in Order against Catalog prices.
- **Order & Fulfillment** — captures Catalog snapshots (price, tax, name, description) into the Quote.
- **Beckn Bridge** — projects Products as `Resource`s, pricing as `Offer`s, categories per the mapping registry.

## Two product modes (per [ADR-0005](../../decisions/0005-catalog-and-product-modeling.md))

A Product is in exactly one of two modes, chosen at creation and **immutable**:

| Mode | Use when… | Structure |
|---|---|---|
| **Matrix** | Variants don't need individual SKUs (e.g., t-shirt sizes; same SKU across all sizes) | One Product with variant-defining attributes (Size, Color); Variants are explicit combinations sharing the parent's SKU. |
| **Flat** | Variants need individual SKUs (e.g., different RAM tiers, each with its own stock and SKU) | Each "variant" is a separate Product with its own SKU. Stores group them via additional Catalogs. |

**Decision rule for the store**: any variant needs its own SKU → use Flat. Otherwise → Matrix.

## Catalogs within a store (per [ADR-0004](../../decisions/0004-store-publication-and-multi-catalog-projection.md) + [ADR-0020](../../decisions/0020-default-catalog-mandatory.md))

A store has:

- **Exactly one Default Catalog**, auto-created with the store, not deletable. **Mandatory membership**: every Product in the store is automatically and permanently a member. There is no exclusion mechanism. *(Per ADR-0020 — the way to hide a Product from Beckn is to set `status = Archived`.)*
- **Zero or more additional Catalogs** — named, scoped to the store, with **opt-in membership** (products are added explicitly via `IncludeProductInCatalog`).

A Product may be in **the Default Catalog (always) + zero or more additional Catalogs**.

All Catalogs project to Beckn — each as a distinct wire `Catalog` object carrying the same `Provider` (the store). BAPs see distinguishable groupings. See [§3.4.1](../03-beckn-integration.md) for the wire shape.

## Key concepts

### Product

Entity invariants:
- `name` — required; `LocalizedText`; unique within store (uniqueness checked on default-locale `id`).
- `description` — required; `LocalizedText`.
- `mode` — `Matrix` | `Flat`; immutable.
- `sku` — optional; unique within store if set.
- `status` — `Draft` | `Active` | `Archived`.
- `base_price` — `Money`, tax-excluded (required for `Active`).
- `tax_rate` — decimal percentage (required for `Active`).
- Derived (cached, auto-recomputed on price/rate change): `tax_amount = round(base_price × tax_rate / 100)`; `published_price = base_price + tax_amount`.
- At least one `ProductCategoryAssignment` required for `Active`.

### ProductVariant (Matrix mode only)

- `product_id`, `attribute_values` (one per parent's `ProductAttribute`)
- `media` (optional; inherits parent's if absent)
- `price_override` (optional; tax-excluded). Variant inherits parent's `tax_rate`.
- No per-variant `tax_rate` — tax category attaches to the Product.

### ProductAttribute (Matrix mode)

- `name` — `LocalizedText` (e.g., `{id: "Ukuran", en: "Size"}`)
- `allowed_values` — ordered list; each value has a locale-neutral identifier and optional `LocalizedText` label.

### PlatformCategory

- Hierarchical taxonomy (platform-defined; System Admin–managed).
- `name` — `LocalizedText`.
- Status: `Active` | `Deprecated`. Cannot be deleted while assignments reference it.
- Stores assign their Products to platform categories; the Bridge derives Beckn `provider.categories[]` from this taxonomy.

### Media

Ordered list of media references per Product (and optionally per Variant). Storage is an Infrastructure concern; the domain knows only references. `alt_text` is `LocalizedText`.

## Lifecycles

### Product

| From → To | Actor | Guard |
|---|---|---|
| (new) → `Draft` | Owner / Admin | none |
| `Draft` → `Active` | Owner / Admin | requires ≥1 category assignment + `base_price` + `tax_rate` |
| `Active` → `Archived` | Owner / Admin | none |
| `Archived` → `Active` | Owner / Admin | requires ≥1 valid (non-deprecated) category |

Forbidden: `Active` → `Draft`, any deletion, mode change.

`Draft`: invisible everywhere regardless of catalog membership.
`Active`: visible based on store state + catalog membership + (for additional catalogs) inclusion.
`Archived`: invisible; retained for order history.

### Variant (Matrix mode)

No independent state machine — variants belong to their parent Product. Removal allowed only if no order references it; otherwise *retired* (kept but flagged).

### PlatformCategory

`Active` → `Deprecated`. Deprecated categories remain referenceable for legacy assignments but aren't selectable for new ones. Deletion only when no assignments reference.

### Catalog (additional)

Created / renamed / deleted by store users. Default Catalog: created with store, never deleted.

## Pricing and tax (per [ADR-0007](../../decisions/0007-pricing-tax-and-vouchers.md))

- All monetary values use the `Money` value object: integer minor units + ISO 4217 currency code.
- A store has **one currency**, set at creation, **immutable** once the store has any Active product.
- Stored on Product: `base_price`, `tax_rate`. Derived: `tax_amount`, `published_price`.
- Variants inherit parent's `tax_rate`; only `price_override` is variant-level.
- Quote construction uses these as inputs but is owned by the Order context — no quoted price stored in Catalog.

## Localization (per [ADR-0008](../../decisions/0008-localization-and-localizedtext.md))

`LocalizedText` fields in Catalog: `Product.name`, `Product.description`, `ProductAttribute.name` + value labels, `Media.alt_text`, `PlatformCategory.name`.

Every `LocalizedText` must have an entry for the platform default locale `id`. Reads use `get(locale)` with fallback to default. Uniqueness checks on `Product.name` use the default-locale value.

## Boundary contracts (highlights)

### Use cases exposed

**Store-scoped (Owner / Admin):**
- `CreateProduct`, `UpdateProduct`, `PublishProduct`, `ArchiveProduct`, `RestoreProduct`
- `AssignProductToCategory`, `UnassignProductFromCategory`
- `AddVariantAttribute`, `AddProductVariant`, `UpdateProductVariant`, `RemoveProductVariant` (Matrix)
- `UpdateProductMedia`, `UpdateVariantMedia`
- `CreateCatalog`, `RenameCatalog`, `DeleteCatalog` (additional Catalogs only)
- `IncludeProductInCatalog`, `RemoveProductFromCatalog` (additional Catalogs only — Default has implicit membership per [ADR-0020](../../decisions/0020-default-catalog-mandatory.md))

**System Admin:**
- `CreatePlatformCategory`, `RenamePlatformCategory`, `MovePlatformCategory`, `DeprecatePlatformCategory`, `DeletePlatformCategory` (only if no assignments)

**Read-side:**
- `ListActiveProductsForStore`, `GetProductDetail`, `ListCatalogsForStore`, `GetCatalogContents`, `GetPlatformCategoryTree`

## Notable rules

- **Cross-store identity is independent.** Two stores selling the same physical SKU maintain two independent Product records. No platform-wide canonical product (per ADR-0005).
- **`Product.mode` is immutable.** A Product that needs per-variant SKUs after going live must be archived and recreated as Flat products.
- **Categorization is platform-defined**, not store-defined. Store-private organization is served by additional Catalogs, not by per-store categories.
- **All Default Catalog membership is implicit** per [ADR-0020](../../decisions/0020-default-catalog-mandatory.md) — there's no `CatalogMembership` row needed for Default. Only additional Catalogs use explicit inclusion rows.
- **Quote / pricing computation lives in Order**, not Catalog. Catalog supplies snapshots; Order constructs the Quote.

## Out of scope (v1)

- **Bundles / kits / composite products** — future.
- **Digital vs. physical goods type taxonomy** — assume physical for v1.
- **Search / discovery implementation** (full-text, facets) — read-side index, infrastructure concern.
- **Media storage and file handling** — Infrastructure Layer.
- **Cross-store deduplication for discovery** — search-layer concern; not domain.
- **Sub-roles on Store Admin** (e.g., "catalog editor only") — would extend the matrix.
- **Time-bound list-price changes** (sales windows on the catalog price) — Vouchers approximate this; future work for direct sale-pricing.
