# 4.6 Order & Fulfillment

The Order context is the **commerce track's integration point**. It composes Catalog (item prices, tax, snapshots), Inventory (Reservations), Promotion (voucher validation and redemption), and Tenancy (store admins) into end-to-end Beckn flows. **The Beckn Bridge is the sole external entry point** for Order use cases (per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)) — buyers always arrive via BAPs over the network.

> Backed by: [ADR-0017](../../decisions/0017-order-and-fulfillment.md) (Order, v2 transactional flow), [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md) (pure BPP — Order.buyer is Beckn-typed only; no first-party Order entry).
> Full entity model, sequence walkthroughs, and Bridge ↔ Order mapping: [`design/order.md`](../../design/order.md).

## Position and ownership

**Owns:**
- `Order` (state machine: `Created` → `Initiated` → `Confirmed` → `Fulfilled`, with `Cancelled` and `Expired` as alternative terminals).
- Embedded `Quote` (line items with **captured snapshots** at quote time; not refreshed).
- Embedded `LineItem`s (captured price, tax, name, description per line).

**Cross-context calls** (via Application-Layer ports per [§2.4](../02-principles.md)):
- **Catalog** → resolve product/variant info, capture LocalizedText snapshots at quote time.
- **Inventory** → `Reserve`, `ConvertReservation`, `ReleaseReservation`.
- **Promotion** → `ValidateVoucher`, `RecordVoucherUsage`, `RevertVoucherUsage`.
- **Identity & Access** — actor attribution for store-admin actions (impersonation-aware per [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md)).

**Cross-context references** (by ID only):
- `Store.id` — every Order belongs to one Store.
- `Product.id` / `ProductVariant.id` — referenced in LineItems.
- `Voucher.id`, `VoucherUsage.id` — referenced when a voucher is applied.
- `User.id` — only for store-admin actor attribution; **never** as the buyer.

**Is consumed by:**
- **Beckn Bridge** — the sole external entry. Translates wire `Contract` messages into Order use cases; projects Orders back to Beckn `Contract` for callbacks.
- **Admin UI** — Store Admins / Org Owners fulfill / cancel orders.
- **Audit** — subscribes to all Order events.

## Order state machine

```
        [new]
          │
          ▼
       Created  ─── TTL passes ──►  Expired  (terminal; reservations released if held)
          │
          │ Initiate  (Beckn /init)
          ▼
       Initiated  ── TTL passes ──► Expired
          │
          │ Confirm
          ▼
       Confirmed  ── MarkPreparing ──► (Confirmed + fulfillment_status=Preparing)
          │   │      MarkShipped    ──► (Confirmed + fulfillment_status=Shipped)
          │   │      MarkFulfilled  ──► Fulfilled (terminal)
          │   │
          │   └─── Cancel ──► Cancelled
          │                    (revert voucher; mark payment Refunded;
          │                     stock NOT returned in v1 — Return is deferred)
          │
          │ Cancel
          ▼
       Cancelled (terminal; reservation released if held; voucher reverted if recorded)
```

Wire mapping (handled by the Bridge's mapping registry):

| Domain state | Wire `Contract.status` |
|---|---|
| `Created`, `Initiated` | `DRAFT` |
| `Confirmed` | `ACTIVE` |
| `Fulfilled` | `COMPLETE` |
| `Cancelled`, `Expired` | `CANCELLED` |

No `Returned` state in v1. No deletion (consistent with [§2.8](../02-principles.md)). Audit retention bucket is **financial** (default ~7 years per [ADR-0014](../../decisions/0014-soft-delete-and-audit.md)).

## Key concepts

### Order

Core fields:
- `id`, `store_id`, `status`
- `quote` — embedded; immutable after Created
- `buyer` — Beckn-typed only (see below)
- `reservation_ids[]` — populated at Initiated
- `voucher_usage_id` — set at Confirmed if a voucher was applied
- `payment_status` — `Pending` | `Authorized` | `Captured` | `Refunded` | `Failed`. Driven by external signals.
- `payment_external_ref` — optional (BAP-supplied or gateway reference)
- `fulfillment_status` — `Pending` | `Preparing` | `Shipped` | `Delivered`
- `fulfillment_note` — optional free-text
- `cancel_reason` — optional
- Timestamps

### Quote (embedded)

- `line_items[]` (see below)
- `voucher_applied?` — `{ voucher_id, code, discount_type, discount_value, discount_amount }`
- `totals` — subtotal, tax_total, discount_total, grand_total
- `currency` — from the Store (immutable per Store)
- `valid_until` — TTL; default **15 minutes** (operational)

### LineItem (embedded)

Each line carries **captured snapshots** that don't auto-refresh:

- `item_ref` — `{type: product, product_id}` (Flat) or `{type: variant, variant_id}` (Matrix)
- `quantity` — integer ≥ 1
- `captured_name`, `captured_description` — `LocalizedText` snapshots
- `captured_base_price`, `captured_tax_rate`, `captured_tax_amount`, `captured_published_price` — `Money` / decimal at quote time
- `line_subtotal` — `Money` = `captured_published_price × quantity`

Snapshots ensure receipt stability — if Catalog prices or LocalizedText change after the Quote, the Order remains as quoted.

### Buyer (Beckn-typed; per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md))

```
buyer = {
  bap_id: string,
  transaction_id: string,
  contact_snapshot?: {           // null at Created; populated at Initiated
    name: LocalizedText,
    email: string,
    phone: string,
    address: ShippingAddress,
  }
}
```

`contact_snapshot` is `null` at `Created` (per v2's "no PII at /select") and populated at `Initiated` from the inbound `/init` payload.

## Cross-context orchestration

The three orchestration use cases live in the Order context and call other contexts via Application-Layer ports with **explicit compensation on failure** (per [ADR-0012](../../decisions/0012-cross-context-consistency.md) — no Saga framework in v1).

### `Order.Initiate`

```
require_capability; load Order; assert status == Created; assert TTL not expired
for each line: Inventory.Reserve(item_ref, quantity, held_by = order_id)
if voucher applied: Promotion.ValidateVoucher(...)
  on failure: release all Reservations, raise
persist: reservation_ids, contact_snapshot; status = Initiated
emit: order.initiated
```

### `Order.Confirm`

```
require_capability; load Order; assert status == Initiated; assert TTL not expired
for each reservation_id: Inventory.ConvertReservation(...)
if voucher: Promotion.RecordVoucherUsage(...); persist voucher_usage_id
status = Confirmed; persist; emit: order.confirmed
```

### `Order.Cancel`

```
require_capability; load Order; assert status in {Created, Initiated, Confirmed}
match status:
  Initiated:  for each reservation_id: Inventory.ReleaseReservation(...)
  Confirmed:  if voucher_usage_id: Promotion.RevertVoucherUsage(...)
              if payment_status == Captured: set Refunded; emit payment_status_changed
status = Cancelled; persist; emit: order.cancelled
```

Detailed pseudocode: [`design/order.md`](../../design/order.md).

## Bridge ↔ Order interface

The Bridge translates each inbound v2 wire message into a domain call:

| Wire (BAP → BPP) | Domain call (Bridge invokes) |
|---|---|
| `/select` (Contract w/ items, optional voucher) | `Order.CreateQuote(store_id, items, voucher_code?, beckn_buyer_ref)` |
| `/init` (Contract w/ consumer details) | `Order.Initiate(order_id, contact_snapshot)` |
| `/confirm` (Contract) | `Order.Confirm(order_id)` |
| `/status` | `Order.GetStatus(order_id)` |
| `/cancel` (with reason) | `Order.Cancel(order_id, reason, by_actor = bridge_principal)` |

The Bridge owns transaction_id correlation, signature verification, and the Order ↔ Contract mapping registry. The Order context is **protocol-naive** — it knows nothing about Beckn vocabulary.

See [§3.6](../03-beckn-integration.md) for the full Bridge ↔ Order interface and the wire ↔ domain mapping table.

## Boundary contracts (highlights)

### Use cases exposed

**Beckn-driven (invoked by the Bridge — the sole external entry per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)):**
- `Order.CreateQuote(store_id, items, voucher_code?, beckn_buyer_ref) → Order`
- `Order.Initiate(order_id, contact_snapshot) → Order`
- `Order.Confirm(order_id) → Order`
- `Order.GetStatus(order_id) → Order`
- `Order.Cancel(order_id, reason, by_actor) → Order`

**Fulfillment (Store Admin via Admin UI):**
- `Order.MarkPreparing(order_id, by_actor)`
- `Order.MarkShipped(order_id, by_actor, fulfillment_note?)`
- `Order.MarkFulfilled(order_id, by_actor)`

**Read-side (capability-gated, for the Admin UI):**
- `Order.ListForStore(store_id, filter, acting_user) → [Order]` — Store Admins / Org Owners see their store's orders.

Full list in [`design/order.md`](../../design/order.md).

### Domain events emitted

`order.quote_created`, `order.initiated`, `order.confirmed`, `order.cancelled`, `order.expired`, `order.marked_preparing`, `order.marked_shipped`, `order.fulfilled`, `order.payment_status_changed`.

Plus `promotion.voucher_usage_reverted` (emitted by Promotion when Order calls `RevertVoucherUsage` on cancel-from-Confirmed).

Full registry: [`design/events.md`](../../design/events.md).

## Notable rules

- **The Bridge is the sole external entry.** No first-party `Order.Place`; no `User`-typed buyer (per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)).
- **Quote snapshots are immutable** once Created. Catalog price changes after issuance don't propagate.
- **Quote has a TTL** (15 min default). After expiry, the Order moves to `Expired`; reservations release if held.
- **Cancellation is pre-fulfillment only** in v1. Post-fulfillment refund / return is deferred.
- **No Saga framework.** Multi-context orchestrations use hand-coded compensation per [ADR-0012](../../decisions/0012-cross-context-consistency.md).
- **Stock is NOT returned on cancel-from-Confirmed** in v1 — that's the deferred Return flow. The voucher usage IS reverted; payment is marked Refunded.
- **Payment is external.** Order tracks `payment_status` from external signals; the BPP never stores card data or processes payments directly.
- **Fulfillment is self-fulfilled** by stores. Logistics integration is deferred.

## Out of scope (v1)

- `/track`, `/update`, `/rate`, `/support` handlers — future transactional surface.
- **Refund / return workflows** post-fulfillment.
- **Payment gateway integration** (PCI scope when needed) — currently external.
- **Platform-managed logistics** — currently self-fulfilled.
- **Multi-shipment / split orders** — Order is one-shot fulfillment.
- **Subscriptions / recurring orders** — would require new modeling.
- **Marketplace fees / payouts to stores** — out of scope.
- **ION extensions** `/raise`, `/reconcile` (grievance / settlement).
