# 4.4 Inventory

The Inventory context owns **whether an item is purchasable right now** — stock counts, reservations, and owner-controlled availability. It's the sibling of Catalog: Catalog answers *what is this product*; Inventory answers *can I sell it right now*.

> Backed by: [ADR-0006](../../decisions/0006-inventory-model.md) (Inventory model — base) and [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md) (anchors and reservation fan-out for Composite + Configurable Products).
> Inventory has no separate sub-design doc — the two ADRs are the full reference.

## Position and ownership

**Owns:**
- `StockLevel` — one per stock-tracked inventory item; carries `stock_count` and `purchasable`. Anchors Standalone Products and `ProductVariant`s of Variant-mode Products.
- `OwnerPurchasability` — one per non-stock-tracked Product (Composite or Configurable); carries `purchasable` only (no count). Per [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md).
- `Reservation` — timed holds against a `StockLevel`.
- `StockMovement` event log — typed history of every stock-affecting action.
- `OwnerPurchasabilityToggled` events — fire when the owner toggles a Composite/Configurable Product's purchasable flag (not a `StockMovement` subtype; carries no delta).

**Cross-context references** (by ID only):
- For `StockLevel`: the `Product.id` (Standalone mode) or `ProductVariant.id` (Variant mode) from Catalog.
- For `OwnerPurchasability`: the `Product.id` (Composite or Configurable mode) from Catalog.
- `Store.id` from Tenancy.

**Is consumed by:**
- **Order & Fulfillment** — calls `Reserve` / `ConvertReservation` / `ReleaseReservation` during the order flow; for Composite and Configurable order lines, the Order context iterates and calls per component / per option-anchored choice.
- **Beckn Bridge** — synchronous queries for availability when projecting catalogs to CDS and `/on_select` quotes; calls the same `GetEffectiveAvailability` use case regardless of Product mode.
- **Admin UI** — owner dashboards for stock levels + purchasability toggles.
- **Audit** — subscribes to `StockMovement` events plus `OwnerPurchasabilityToggled`.

**Subscribes to:**
- Catalog product/variant lifecycle events (`product_created`, `product_variant_added`, `product_archived`, `product_variant_removed`, `product_restored`). The subscriber dispatches by Product mode: `StockLevel` for Standalone / Variant; `OwnerPurchasability` for Composite / Configurable. Component / choice-group / choice mutations are *not* subscribed — they affect computed availability but don't change the anchor.

## Key concepts

### StockLevel (stock-tracked anchors)

One per Standalone Product or `ProductVariant` of a Variant-mode Product.

- `id`, `store_id`, `inventory_item_ref` (opaque pointer to Product or Variant)
- `stock_count` — integer ≥ 0; physical units available
- `purchasable` — boolean, owner-controlled; default `true`
- `status` — `Active` | `Inactive` (`Inactive` when the underlying Catalog item is archived)
- Timestamps

### OwnerPurchasability (non-stock-tracked anchors, per [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md))

One per Composite or Configurable Product. No count — these Products don't have a meaningful "stock_count" of their own (Composite availability derives from components; Configurable availability derives from Required choice-group completability).

- `id`, `store_id`, `product_ref` (opaque pointer to Composite or Configurable Product)
- `purchasable` — boolean, owner-controlled; default `true`
- `status` — `Active` | `Inactive`
- Timestamps

### Reservation

Temporary hold against a `StockLevel`. (`OwnerPurchasability` has no Reservations — composites and configurables fan out to their underlying StockLevels.)

- `id`, `stock_level_id`, `quantity` (≥ 1)
- `held_by_ref` — opaque reference to the holder (Order's transaction/cart identifier)
- `expires_at` — timestamp
- `state` — `Active` | `Converted` | `Released`

### Effective availability (computed per Product mode)

The Inventory `GetEffectiveAvailability(anchor_ref)` use case dispatches by mode internally; callers don't need to know which formula applies.

**Standalone / Variant** (anchor: `StockLevel`):
```
active_reservations    = sum of Reservation.quantity where state = Active
available_for_purchase = purchasable AND (stock_count − active_reservations) > 0
available_quantity     = max(0, stock_count − active_reservations) if purchasable
                         else 0
```

**Composite** (anchor: `OwnerPurchasability`):
```
for each ProductComponent c:
    component_units(c) = floor(c.component_anchor.available_quantity / c.quantity)
available_for_purchase = OwnerPurchasability.purchasable
                          AND min(component_units(c) for all c) > 0
available_quantity     = min(component_units(c) for all c) if purchasable
                         else 0
```
"Weakest component wins."

**Configurable** (anchor: `OwnerPurchasability`):
```
for each ChoiceGroup g where g.selection_type = RequiredSingle:
    group_completable(g) = ∃ Choice c in g where
                            c.option_product_ref is null
                            OR c.option_product_ref.available_for_purchase
available_for_purchase = OwnerPurchasability.purchasable
                          AND every RequiredSingle group has group_completable = true
available_quantity     = unbounded if available_for_purchase else 0
```
`OptionalSingle` / `OptionalMultiple` groups don't gate availability.

The Bridge, Admin UI, and Order context all compute these via synchronous query against Inventory. There is no cached projection in v1.

## Lifecycles

### StockLevel and OwnerPurchasability

Both anchor types share the same lifecycle shape:

- (new) → `Active` (auto-created when a Product or Variant is created in Catalog; subscriber dispatches by mode to create the right anchor type)
- `Active` → `Inactive` (cascaded when the Catalog item is archived; new reservations / sales rejected; history retained)
- `Inactive` → `Active` (cascaded when the Catalog item is restored)

No deletion (per [§2.8](../02-principles.md)).

### Reservation

| From → To | Trigger |
|---|---|
| (new) → `Active` | Order `Initiate` (Beckn `/init`) or equivalent first-party checkout. For Composite order lines, one Reservation per `ProductComponent`. For Configurable order lines, one Reservation per chosen `Choice` that carries an `option_product_ref` (label-only choices create none). All reservations from one line share a `held_by_ref`. |
| `Active` → `Converted` | Order `Confirm` — `stock_count` decremented atomically. For Composite / Configurable lines: all reservations from the line convert atomically (all-or-nothing); if any conversion fails, already-converted reservations are rolled back. |
| `Active` → `Released` | Order cancel, OR `expires_at` passed. Fan-out lines release all their reservations atomically. |

The exact Beckn-flow trigger points are owned by [Order](4.6-order.md) (per [ADR-0017](../../decisions/0017-order-and-fulfillment.md)); Inventory provides the primitive. Fan-out logic lives in the Order context's orchestration (per [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md)).

## Stock-movement events

Every stock-affecting action emits one typed event against a `StockLevel`:

| Type | When | Stock delta |
|---|---|---|
| `Received` | Owner records incoming stock | +N |
| `Sold` | Reservation → Converted at order confirm | −N |
| `Returned` | Order return (future; not in v1) | +N |
| `Corrected` | Manual adjustment with reason note | ±N |
| `Reserved` | Reservation Active | 0 (logical) |
| `Released` | Reservation Released | 0 |
| `PurchasableToggled` | Owner flipped `StockLevel.purchasable` | 0 |

For Composite confirms, the `Sold` event fans out — one per component, each on the component's `StockLevel`. For Configurable confirms, one `Sold` per chosen option-anchored Choice on the referenced anchor's `StockLevel`.

Each event carries actor, timestamp, item reference, signed delta (or null for logical events), and optional reason. Audit ingests this stream.

## Owner-purchasability events (per [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md))

A separate event stream fires against `OwnerPurchasability` anchors (Composite and Configurable Products):

| Type | When | Stock delta |
|---|---|---|
| `OwnerPurchasabilityCreated` | Inventory auto-creates the anchor on Product creation | n/a |
| `OwnerPurchasabilityInactivated` | Cascaded on Product archive | n/a |
| `OwnerPurchasabilityToggled` | Owner flipped `OwnerPurchasability.purchasable` | n/a |

These are *not* `StockMovement` subtypes — they carry no delta. Audit ingests them like any other domain event.

## Boundary contracts (highlights)

### Use cases exposed (Application Layer)

**Owner / Store Admin:**
- `AdjustStock(item_ref, delta, reason)` — emits `Received` or `Corrected` (StockLevel anchors only)
- `SetPurchasable(item_ref, value)` — emits `PurchasableToggled` (StockLevel) or `OwnerPurchasabilityToggled` (OwnerPurchasability), dispatched by anchor type
- `GetStockLevel(item_ref)` (StockLevel anchors only)

**Called by Order context:**
- `Reserve(item_ref, quantity, held_by_ref) → Reservation`
- `ConvertReservation(reservation_id)` — atomic decrement
- `ReleaseReservation(reservation_id)`

The Order context iterates and calls these per component (Composite line) or per option-anchored choice (Configurable line); fan-out semantics live in Order's orchestration.

**Called by Bridge / Admin UI:**
- `GetEffectiveAvailability(anchor_ref)` — synchronous; dispatches by Product mode; returns `available_for_purchase` and `available_quantity`. Replaces the v1 `GetAvailability` use case.
- `BulkGetEffectiveAvailability([anchor_refs])` — for catalog projection at publish time

**Called automatically (subscriptions):**
- `OnProductCreated`, `OnProductArchived`, `OnProductRestored` — manage the appropriate anchor type by mode (`StockLevel` for Standalone / Variant, `OwnerPurchasability` for Composite / Configurable)
- `OnProductVariantAdded`, `OnProductVariantRemoved` — `StockLevel` per variant

### Domain events emitted

Stock-tracked: `inventory.stock_level_created`, `inventory.stock_level_inactivated`, `inventory.stock_received`, `inventory.stock_sold`, `inventory.stock_returned`, `inventory.stock_corrected`, `inventory.stock_reserved`, `inventory.stock_released`, `inventory.purchasable_toggled`.

Owner purchasability: `inventory.owner_purchasability_created`, `inventory.owner_purchasability_inactivated`, `inventory.owner_purchasability_toggled`.

Full registry: [`design/events.md`](../../design/events.md).

## Notable rules

- **Two anchor types** (per [ADR-0024](../../decisions/0024-inventory-for-composite-and-configurable-products.md)): `StockLevel` for stock-tracked Products (Standalone, Variant variants); `OwnerPurchasability` for non-stock-tracked Products (Composite, Configurable). Same `Reservation` primitive serves both indirectly (Reservations always anchor to a `StockLevel`).
- **Anchors are Catalog entities by ID.** Inventory holds opaque references; no joins (per [§2.4](../02-principles.md)).
- **Single store-scoped inventory in v1.** No multi-location / multi-warehouse.
- **No backorders.** Cannot sell beyond `stock_count`. If preorders ever land, they'd be a per-item `allow_backorder` flag.
- **Stock decrement happens only via Reservation conversion** at order confirm, or via explicit `Corrected` adjustment, or via `Received` (incoming stock). Direct stock writes outside these paths are forbidden.
- **Composite / Configurable confirms fan out** to per-component / per-option-anchored Reservations. All-or-nothing atomicity preserved by the Order orchestration; Inventory provides the primitive.
- **Reservation timeout is operational config**, not architectural.
- **Effective availability is computed on demand** — no cached availability snapshot in v1. The `GetEffectiveAvailability` use case hides per-mode dispatch.

## Out of scope (v1)

- **Multi-location inventory** (Warehouse / Location concept).
- **Backorders / preorders** (`allow_backorder` flag).
- **Low-stock thresholds and alerts** — Admin UI concern.
- **Per-component reservation pools** (separate "bundle pool" vs. standalone pool for the same anchor). v1 uses a single pool per `StockLevel`.
- **Daily capacity for Configurable Products** ("I can make 30 custom cakes today"). Not in v1; if needed, would be a separate `DailyCapacity` entity.
- **Inventory reconciliation flows** (physical count vs. system) — handled via `Corrected` events; operational.
- **Supplier integrations / automated receiving** — future; would surface as `Received` events from an integration layer.
- **Event-driven availability projection** — added later if synchronous queries don't scale.
- **Cross-store unified inventory** — each store's inventory is independent.
