# 4.4 Inventory

The Inventory context owns **whether an item is purchasable right now** — stock counts, reservations, and owner-controlled availability. It's the sibling of Catalog: Catalog answers *what is this product*; Inventory answers *can I sell it right now*.

> Backed by: [ADR-0006](../../decisions/0006-inventory-model.md) (Inventory model).
> Inventory has no separate sub-design doc — the ADR is the full reference.

## Position and ownership

**Owns:**
- `StockLevel` — one per inventory item; carries `stock_count` and `purchasable`.
- `Reservation` — timed holds against a `StockLevel`.
- `StockMovement` event log — typed history of every stock-affecting action.

**Cross-context references** (by ID only):
- `Product.id` (Flat mode) or `ProductVariant.id` (Matrix mode) from Catalog — the inventory anchor.
- `Store.id` from Tenancy.

**Is consumed by:**
- **Order & Fulfillment** — calls `Reserve` / `ConvertReservation` / `ReleaseReservation` during the order flow.
- **Beckn Bridge** — synchronous queries for availability when projecting catalogs to CDS and `/on_select` quotes.
- **Admin UI** — owner dashboards for stock levels.
- **Audit** — subscribes to `StockMovement` events.

**Subscribes to:**
- Catalog product/variant lifecycle events (auto-create `StockLevel` on Product creation; mark `Inactive` on Archive).

## Key concepts

### StockLevel

One per inventory item (Flat Product or Matrix Variant).

- `id`, `store_id`, `inventory_item_ref` (opaque pointer to Product or Variant)
- `stock_count` — integer ≥ 0; physical units available
- `purchasable` — boolean, owner-controlled; default `true`
- `status` — `Active` | `Inactive` (`Inactive` when the underlying Catalog item is archived)
- Timestamps

### Reservation

Temporary hold against a `StockLevel`.

- `id`, `stock_level_id`, `quantity` (≥ 1)
- `held_by_ref` — opaque reference to the holder (Order's transaction/cart identifier)
- `expires_at` — timestamp
- `state` — `Active` | `Converted` | `Released`

### Effective availability (computed at read time)

For any inventory item:

```
active_reservations = sum of Reservation.quantity where state = Active
                      for this StockLevel
available_for_purchase = purchasable AND (stock_count − active_reservations) > 0
available_quantity     = max(0, stock_count − active_reservations)  if purchasable
                         else 0
```

The Bridge, Admin UI, and Order context all compute these via synchronous query against Inventory. There is no cached projection in v1.

## Lifecycles

### StockLevel

- (new) → `Active` (auto-created when a Product or Variant is created in Catalog)
- `Active` → `Inactive` (cascaded when the Catalog item is archived; new reservations / sales rejected; history retained)
- `Inactive` → `Active` (cascaded when the Catalog item is restored)

No deletion (per [§2.8](../02-principles.md)).

### Reservation

| From → To | Trigger |
|---|---|
| (new) → `Active` | Order `Initiate` (Beckn `/init`) or equivalent first-party checkout |
| `Active` → `Converted` | Order `Confirm` — `stock_count` is decremented atomically; the reservation row is retained for audit |
| `Active` → `Released` | Order cancel, OR `expires_at` passed |

The exact Beckn-flow trigger points are owned by [Order](4.6-order.md) (per [ADR-0017](../../decisions/0017-order-and-fulfillment.md)); Inventory provides the primitive.

## Stock-movement events

Every stock-affecting action emits one typed event:

| Type | When | Stock delta |
|---|---|---|
| `Received` | Owner records incoming stock | +N |
| `Sold` | Reservation → Converted at order confirm | −N |
| `Returned` | Order return (future; not in v1) | +N |
| `Corrected` | Manual adjustment with reason note | ±N |
| `Reserved` | Reservation Active | 0 (logical) |
| `Released` | Reservation Released | 0 |
| `PurchasableToggled` | Owner flipped the `purchasable` flag | 0 |

Each event carries actor, timestamp, item reference, signed delta (or null for logical events), and optional reason. Audit ingests this stream.

## Boundary contracts (highlights)

### Use cases exposed (Application Layer)

**Owner / Store Admin:**
- `AdjustStock(item_ref, delta, reason)` — emits `Received` or `Corrected`
- `SetPurchasable(item_ref, value)` — emits `PurchasableToggled`
- `GetStockLevel(item_ref)`

**Called by Order context:**
- `Reserve(item_ref, quantity, held_by_ref) → Reservation`
- `ConvertReservation(reservation_id)` — atomic decrement
- `ReleaseReservation(reservation_id)`

**Called by Bridge / Admin UI:**
- `GetAvailability(item_ref)` — synchronous; returns `available_for_purchase` and `available_quantity`
- `BulkGetAvailability([item_refs])` — for catalog projection at publish time

**Called automatically (subscriptions):**
- `OnProductCreated`, `OnProductArchived`, `OnProductRestored` — manage `StockLevel` lifecycle
- `OnProductVariantAdded`, `OnProductVariantRemoved` — same for Matrix variants

### Domain events emitted

`inventory.stock_level_created`, `inventory.stock_level_inactivated`, `inventory.stock_received`, `inventory.stock_sold`, `inventory.stock_returned`, `inventory.stock_corrected`, `inventory.stock_reserved`, `inventory.stock_released`, `inventory.purchasable_toggled`.

Full registry: [`design/events.md`](../../design/events.md).

## Notable rules

- **Anchors are Catalog entities by ID.** Inventory holds opaque references; no joins (per [§2.4](../02-principles.md)).
- **Single store-scoped inventory in v1.** No multi-location / multi-warehouse.
- **No backorders.** Cannot sell beyond `stock_count`. If preorders ever land, they'd be a per-item `allow_backorder` flag.
- **Stock decrement happens only via Reservation conversion** at order confirm, or via explicit `Corrected` adjustment, or via `Received` (incoming stock). Direct stock writes outside these paths are forbidden.
- **Reservation timeout is operational config**, not architectural.
- **Effective availability is computed on demand** — no cached availability snapshot in v1.

## Out of scope (v1)

- **Multi-location inventory** (Warehouse / Location concept).
- **Backorders / preorders** (`allow_backorder` flag).
- **Low-stock thresholds and alerts** — Admin UI concern.
- **Inventory reconciliation flows** (physical count vs. system) — handled via `Corrected` events; operational.
- **Supplier integrations / automated receiving** — future; would surface as `Received` events from an integration layer.
- **Event-driven availability projection** — added later if synchronous queries don't scale.
- **Cross-store unified inventory** — each store's inventory is independent.
