# 6.8 Audit — playbook

How to implement the Audit context. Audit is a **downstream sink** — it subscribes broadly to the domain event stream and produces append-only `AuditRecord`s for compliance and operational history. It emits nothing, mutates nothing (except PII scrubbing under a narrow role).

> **Read first**: [handoff §4.7 Audit](../../handoff/04-bounded-contexts/4.7-audit.md), [`design/audit.md`](../../design/audit.md), [`design/pii.md`](../../design/pii.md), [ADR-0014](../../decisions/0014-soft-delete-and-audit.md), [ADR-0015](../../decisions/0015-pii-and-right-to-erasure.md), [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md).

## Entities

### `AuditRecord` (append-only, immutable at the DB role level)

| Field | Notes |
|---|---|
| `audit_id` | Internal opaque |
| `event_id` | From source event envelope; dedup key |
| `event_name` | E.g., `tenancy.store_status_changed` |
| `event_version` | Schema version of the source event |
| `recorded_at` | When Audit ingested the event |
| `occurred_at` | From source event |
| `actor` | `{ user_id, impersonated_user_id, active_org_id, active_store_id }` per [§5.1.6 of handoff](../../handoff/05-cross-cutting.md) |
| `aggregate_type` | E.g., `Store`, `Product`, `Order` |
| `aggregate_id` | The affected aggregate |
| `before_state` | Optional; for change events with prior state |
| `after_state` | Optional; for change events with new state |
| `summary` | Human-readable rendering of the event |
| `correlation_id` | Traces causally related events from one operation |
| `source_envelope` | Full original event envelope (archival snapshot) |
| `retention_category` | Drives sweep; derived from `event_name` per registry |

**Invariants enforced at the DB role level** (not application code):
- `audit_subscriber` role: INSERT only. No UPDATE. No DELETE.
- `audit_pii_scrubber` role: field-level UPDATE on `source_envelope` only. Nothing else.
- `audit_cleanup` role: DELETE only, row-filtered (`recorded_at + retention < now()`).
- `audit_reader` role: SELECT only.

No role has UPDATE on any field other than `source_envelope`.

**Lifecycle:** records are immutable once written; the only state transition is **expiry-and-deletion** by the retention sweep.

## Subscription scope

Audit subscribes to **all mutation events** across all contexts via a single broad subscription:

```
ingest-all-events.ts → AuditRecordWriterPort.insert(toAuditRecord(event))
```

Per [§4.7 of handoff](../../handoff/04-bounded-contexts/4.7-audit.md):

- Configurable per-event-name exclusions handle noise (e.g., `identity.session_active_store_set` is high-volume and low-information — exclude via config).
- Inbox dedup is per the standard pattern (per [§5.3.6 of handoff](../../handoff/05-cross-cutting.md)) keyed by `event_id`.

## Access matrix (enforced by `access-matrix.ts`)

Per [§4.7 of handoff](../../handoff/04-bounded-contexts/4.7-audit.md) + [ADR-0002](../../decisions/0002-authorization-tiers-and-matrix.md):

| Reader | Records visible |
|---|---|
| **System Admin** | All — platform-wide read |
| **Platform-scoped** with `audit.read.platform` | All (or subset per finer capability) |
| **Org Owner / Store Admin** | `aggregate_type` belongs to a store in their Org, OR `actor.active_org_id` is their Org |
| **User** | `actor.user_id == self.id` OR `actor.impersonated_user_id == self.id` |
| **(Beckn buyers)** | Not applicable — buyers are not Users; they cannot read audit |

The access matrix runs in the Application Layer of Audit; read use cases enforce the filter BEFORE returning records. The `audit_reader` DB role permits SELECT, but the application-layer filter constrains the rows returned.

## Retention (per category)

Per `event_name` → `retention_category` mapping (lives in `shared/domain-events/registry.ts` per [§5.2.5 of handoff](../../handoff/05-cross-cutting.md)):

| Category | Default retention |
|---|---|
| `financial` (Order, Voucher redemption) | ~7 years |
| `inventory` (stock adjustments) | ~3 years |
| `business_state` (Store, Product, Membership lifecycle) | ~2 years |
| `identity_session` (Identity events) | ~1 year |
| `catalog_routine` (media updates, etc.) | ~1 year |

Tunable by compliance; values are operational config, not hardcoded.

## Ports declared

| Port | DB role | Purpose |
|---|---|---|
| `AuditRecordWriterPort` | `audit_subscriber` | INSERT only — used by `ingest-event` |
| `AuditRecordReaderPort` | `audit_reader` | SELECT only — used by read use cases |
| `AuditPiiScrubberPort` | `audit_pii_scrubber` | UPDATE on `source_envelope` only — used by `scrub-audit-pii` |
| `AuditCleanupPort` | `audit_cleanup` | DELETE only (row-filtered) — used by `retention-sweep` job |

**Provides** to other contexts: nothing publicly. Audit is a sink.

Identity calls `AuditPiiScrubberPort` via a cross-context port adapter during the `ScrubUser` orchestration ([§5.6.2 of handoff](../../handoff/05-cross-cutting.md)).

## Use cases

### Subscriber-driven

| # | Use case | Caller | Notes |
|---|---|---|---|
| 1 | `IngestEvent(event)` | The dispatcher (broad subscription) | Idempotent by `event_id`; transforms envelope into AuditRecord and INSERTs via `AuditRecordWriterPort`. |

### Read-side (capability-gated)

| # | Use case | Capability | Notes |
|---|---|---|---|
| 2 | `GetAuditRecord(audit_id, acting_user)` → `AuditRecord \| NotAllowed \| NotFound` | `audit.read` (any tier) | Access matrix filter applied. |
| 3 | `ListRecordsForStore(store_id, filter, acting_user)` | `audit.read.store` | Returns records where aggregate is in the store OR actor's `active_store_id` matches. |
| 4 | `ListRecordsForUser(user_id, filter, acting_user)` | Self OR `audit.read.user` (System Admin) | Returns records where actor.user_id = user_id OR actor.impersonated_user_id = user_id. |
| 5 | `SearchRecords(query, filter, acting_user)` | `audit.read.platform` | Platform-scope; System Admin / cleared Platform-scoped operators. |

### Maintenance

| # | Use case | Caller | Notes |
|---|---|---|---|
| 6 | `ScrubAuditPii(user_id)` | Identity's `ScrubUser` orchestration | Walks affected AuditRecords; replaces PII fields in `source_envelope` per the catalog; via `audit_pii_scrubber` role only. Idempotent. |
| 7 | `RetentionSweep()` | Background job | Per category: DELETE where `recorded_at + retention < now()` via `audit_cleanup` role. |

## Migration sketch

`migrations/0009__audit.sql`:

```sql
-- Roles (these may live in a separate role-management migration; shown here for completeness)
CREATE ROLE audit_subscriber NOLOGIN;
CREATE ROLE audit_reader NOLOGIN;
CREATE ROLE audit_pii_scrubber NOLOGIN;
CREATE ROLE audit_cleanup NOLOGIN;

CREATE TABLE audit_records (
  audit_id text PRIMARY KEY,
  event_id text NOT NULL UNIQUE,                -- dedup key
  event_name text NOT NULL,
  event_version int NOT NULL,
  recorded_at timestamptz NOT NULL DEFAULT now(),
  occurred_at timestamptz NOT NULL,
  actor jsonb NOT NULL,                         -- { user_id, impersonated_user_id, active_org_id, active_store_id }
  aggregate_type text NOT NULL,
  aggregate_id text NOT NULL,
  before_state jsonb,
  after_state jsonb,
  summary text NOT NULL,
  correlation_id text,
  source_envelope jsonb NOT NULL,               -- archival snapshot; PII scrubbable via audit_pii_scrubber role
  retention_category text NOT NULL              -- 'financial' | 'inventory' | 'business_state' | 'identity_session' | 'catalog_routine'
);

CREATE INDEX idx_audit_aggregate ON audit_records (aggregate_type, aggregate_id);
CREATE INDEX idx_audit_actor_user ON audit_records ((actor->>'user_id'));
CREATE INDEX idx_audit_actor_org ON audit_records ((actor->>'active_org_id'));
CREATE INDEX idx_audit_recorded_at ON audit_records (recorded_at);
CREATE INDEX idx_audit_correlation ON audit_records (correlation_id) WHERE correlation_id IS NOT NULL;

-- Role grants
GRANT INSERT ON audit_records TO audit_subscriber;
GRANT SELECT ON audit_records TO audit_reader;
GRANT UPDATE (source_envelope) ON audit_records TO audit_pii_scrubber;
GRANT DELETE ON audit_records TO audit_cleanup;
-- Note: no role gets UPDATE on any field other than source_envelope.
```

The DB role separation is the entire enforcement story for the append-only invariant. Don't rely on application-level checks — those drift.

## Implementation order (within this context)

### Phase 1 (subscription stub)

1. **`audit_records` schema** + DB role setup (migration).
2. **`AuditRecordWriterPort`** + Drizzle adapter using `audit_subscriber` role.
3. **`ingest-all-events.ts`** broad subscription + `IngestEvent` use case (idempotent by `event_id`).
4. Verify by ensuring all events from Phase 1 Identity (e.g., `user_provisioned`, `session_created`) land as AuditRecords.

### Phase 7 (full context)

5. **`AuditRecordReaderPort`** + Drizzle adapter using `audit_reader` role.
6. **`access-matrix.ts`** service — translates `acting_user` to the visibility filter.
7. **Read use cases** (`GetAuditRecord`, `ListRecordsForStore`, `ListRecordsForUser`, `SearchRecords`) — capability-gated; filter via access matrix.
8. **`AuditPiiScrubberPort`** + adapter using `audit_pii_scrubber` role.
9. **`pii-scrubber.ts`** service — walks `source_envelope`; replaces PII fields per `design/pii.md`.
10. **`ScrubAuditPii` use case** — called by Identity's `ScrubUser` orchestration via cross-context port.
11. **`AuditCleanupPort`** + adapter using `audit_cleanup` role.
12. **`retention-sweep.ts` job** — scheduled; per-category deletion.
13. **Admin UI surfaces** — audit viewer per store, per user, platform-wide search.

## Test checklist

**Domain tests**:
- [ ] `AccessMatrix` correctness across all reader types (System Admin / Platform / Org Owner / Store Admin / User / non-User).
- [ ] `PiiScrubber` correctly walks nested JSON and replaces only PII-tagged fields per the catalog.

**Application tests**:
- [ ] `IngestEvent` is idempotent by `event_id` (replaying the same event produces one AuditRecord).
- [ ] `GetAuditRecord` returns `NotAllowed` when the access matrix rejects.
- [ ] `ListRecordsForStore` filters correctly per Org Owner / Store Admin scope.
- [ ] `ListRecordsForUser` returns records where actor.user_id matches OR impersonated_user_id matches.
- [ ] `ScrubAuditPii` is idempotent (running twice doesn't double-scrub or corrupt).
- [ ] `RetentionSweep` deletes only records past their category's retention.

**Infrastructure tests**:
- [ ] `audit_subscriber` role cannot UPDATE (test: attempt UPDATE; expect error).
- [ ] `audit_subscriber` role cannot DELETE (test: attempt DELETE; expect error).
- [ ] `audit_pii_scrubber` role can UPDATE `source_envelope` (test: succeeds).
- [ ] `audit_pii_scrubber` role cannot UPDATE other fields (test: attempt UPDATE on `summary`; expect error).
- [ ] `audit_cleanup` role can DELETE rows past retention; cannot DELETE rows within retention (test via row-level check or application-side query).
- [ ] `audit_reader` role cannot INSERT, UPDATE, or DELETE.

**Subscriber tests**:
- [ ] Subscribed to all expected event names per `shared/domain-events/registry.ts`.
- [ ] Excluded events (per config) are not ingested.
- [ ] Inbox dedup prevents double-write on event redelivery.

## Gotchas

- **Append-only is enforced at the DB role level**, not in application code ([§4.7 of handoff](../../handoff/04-bounded-contexts/4.7-audit.md)). Application code that "tries to UPDATE" should fail at the DB. Don't add application-level "no update" checks as a substitute.
- **PII scrubbing is the ONLY permitted UPDATE.** Any other "fix the audit log" request gets a hard no — that's the architectural commitment ([§4.7 of handoff](../../handoff/04-bounded-contexts/4.7-audit.md)).
- **Audit emits NOTHING.** It is a sink. Downstream consumers (analytics, alerting) subscribe to the original event stream, not to Audit.
- **`source_envelope` is the archival snapshot.** Subscribers reading old records may see old event schema versions; tolerate this. Don't normalize the envelope over time.
- **Cryptographic chaining is deferred** ([§4.7 deferred items in handoff](../../handoff/07-open-issues.md)). Don't pre-build it.
- **Retention is per category, not per record.** Categorize each event type in the registry at the time the event is introduced. Don't compute category at audit-read time.
- **Access matrix runs in the Application Layer.** The `audit_reader` DB role permits broad SELECT; the matrix filters before returning. Don't try to enforce access at the DB-row level (too rigid for the rules).
- **One AuditRecord per consumed event.** No higher-level "audit operations" composition in v1 ([§7.2.7 of handoff](../../handoff/07-open-issues.md) — deferred).
- **Subscription must be broad and stable.** If a new event is added to the registry but not subscribed by Audit, it doesn't get audited. Test that the subscription matches the registry.
- **Excluded events go to config**, not code. Operators can adjust without a deploy.
- **`ScrubAuditPii` is called from Identity**, not initiated by Audit. The orchestration entry point is Identity's `ScrubUser` ([§5.6.2 of handoff](../../handoff/05-cross-cutting.md)).
- **Cross-tenant audit summarization is out of scope** ([§7.2.7 of handoff](../../handoff/07-open-issues.md)). Audit is for compliance + history, not analytics.
