# 6.7 Beckn Bridge — playbook

How to implement the Beckn Bridge. The Bridge is **not a bounded context** — it's a specialized Interface-Layer adapter, the sole place Beckn protocol vocabulary is permitted. Every other context in the system is Beckn-naive by design ([§4 of CLAUDE.md](../../CLAUDE.md)).

> **Read first**: [handoff §3 Beckn integration](../../handoff/03-beckn-integration.md), [§2.7 of CLAUDE.md](../../CLAUDE.md) (Bridge position), [§4 of CLAUDE.md](../../CLAUDE.md) (full Bridge rules), **[ADR-0022](../../decisions/0022-onix-protocol-gateway.md) (ONIX gateway — current architecture)**, [ADR-0001](../../decisions/0001-bpp-network-identity.md), [ADR-0017](../../decisions/0017-order-and-fulfillment.md), [ADR-0019](../../decisions/0019-manual-catalog-republication.md).

## At a glance

| Aspect | Detail |
|---|---|
| Phase landed | [Phase 6](../05-phases.md) — Beckn Bridge |
| Architectural position | Interface-Layer adapter, sibling of `contexts/` and `admin-api/` |
| Owns | The mapping registry + protocol mechanics (BPP-side). **No domain.** |
| Sole Beckn-vocabulary zone in the BPP | Beckn vocabulary lives only here within the BPP. Cryptographic signing + network HTTP move to ONIX per [ADR-0022](../../decisions/0022-onix-protocol-gateway.md). |
| External systems | **ONIX** (vendor binary, per-BPP). The Bridge speaks only to ONIX; ONIX handles registry / CDS / BAP callback HTTP on the network. |
| Cross-context calls | Invokes use cases from every context (Order, Catalog, Inventory availability reads) |
| **Emits no domain events** | Bridge emits Beckn protocol messages (to ONIX), not domain events |
| First migration | `0008__bridge.sql` (protocol-boundary idempotency + outbound queue) |

**Notes on what moved**:
- Removed: `protocol/signing.ts` (ONIX signs outbound — see [ADR-0022](../../decisions/0022-onix-protocol-gateway.md)).
- `protocol/verification.ts` **stays** — narrower scope (inbound re-verification only, for CounterSignature attestation).
- New: `onix-client/` is the single thin adapter for outbound HTTP. Replaces direct BAP-callback / CDS-publish HTTP clients.
- New: `protocol/ion-error-registry.ts` loads `ion-specs/errors/registry.json` at startup; provides `lookup(code) → { http_status, title, resolution, ... }` and reverse `domainError → ION-XXXX`.
- New: `protocol/ack-builder.ts` constructs synchronous responses (`Ack`, `AckNoCallback`, `Nack`) with the CounterSignature attesting BPP authentication.

## What's NOT in the Bridge

- **Domain entities.** The Bridge has none. It invokes use cases.
- **Business rules.** "An item is available if stock > 0" is a domain rule. The Bridge asks the Application Layer.
- **Direct persistence.** The Bridge writes only to its own protocol-boundary tables (idempotency, outbound queue). It reads through Application-Layer use cases.
- **Domain events.** The Bridge emits Beckn messages on the wire, not domain events.
- **Outbound signing.** ONIX signs. The Bridge POSTs unsigned envelopes to ONIX.
- **ion-specs schema validation at network door.** ONIX validates. The Bridge may still validate defensively at startup or in tests; not on the hot path.
- **Beckn registry interactions.** ONIX manages. The Bridge does not hold registry credentials.
- **Direct HTTP to BAP callback URLs.** ONIX forwards. The Bridge POSTs to ONIX.
- **Direct HTTP to CDS publish endpoints.** ONIX forwards. The Bridge POSTs `/catalog/publish` payload to ONIX.

## Network identity (per [ADR-0001](../../decisions/0001-bpp-network-identity.md) + [ADR-0022](../../decisions/0022-onix-protocol-gateway.md))

The platform appears on the Beckn network as **a single BPP**. **ONIX is the network-visible endpoint** — `bpp-uri` resolves to ONIX. Operational config:

| Config | BPP-side | ONIX-side |
|---|---|---|
| `bpp-id` | Deploy-time env var (used in `context.bpp_id`) | (consumed for routing) |
| `bpp-uri` | Deploy-time env var; value = ONIX network-facing URL | (this is ONIX itself) |
| `ONIX_ENDPOINT` (BPP-facing URL of ONIX) | Deploy-time env var | (this is ONIX's private listener) |
| Signing key material | — | Vendor config / secrets |
| Registry credentials | — | Vendor config / secrets |
| Registry endpoint | — | Vendor config |
| CDS endpoint(s) | — | Vendor config |

Stores project as Beckn `provider` nodes within BPP responses; provider IDs are deterministically derived from internal store identifiers (mapping lives in `store-to-provider.ts`). The mapping is unchanged by [ADR-0022](../../decisions/0022-onix-protocol-gateway.md); ONIX is transparent on `context` field contents.

## Use cases (handlers + projections)

The Bridge has no domain use cases. Its "use cases" are inbound handlers (calls into the Application Layer) and outbound projections (calls out to the network).

### Inbound handlers

| Handler | BAP → BPP | Invokes Application use case |
|---|---|---|
| `handleSelect(payload)` | `/select` (Contract w/ items, optional voucher) | `Order.CreateQuote(store_id, items, voucher_code?, beckn_buyer_ref)` |
| `handleInit(payload)` | `/init` (Contract w/ consumer details) | `Order.Initiate(order_id, contact_snapshot)` |
| `handleConfirm(payload)` | `/confirm` (Contract) | `Order.Confirm(order_id)` |
| `handleStatus(payload)` | `/status` | `Order.GetStatus(order_id)` |
| `handleCancel(payload)` | `/cancel` (with reason) | `Order.Cancel(order_id, reason, by_actor = bridge_principal)` |

Each handler does, in order:

1. **Verify signature** (`protocol/verification.ts`) against the registry-fetched BAP key.
2. **Validate payload** against the ion-specs schema for the declared protocol version.
3. **Idempotency check** at the protocol boundary by `(transaction_id, message_id)`. Duplicate → return cached ack, no domain call.
4. **Extract business intent** via `mapping-registry/` (e.g., `Contract → CreateQuoteInput`).
5. **Invoke the Application use case** with domain-shaped inputs.
6. **Return immediate acknowledgement** (Beckn is async — substantive response is delivered via the matching `/on_*` callback).
7. **Schedule outbound projection** (enqueue the corresponding `on-*` callback for asynchronous dispatch).

### Outbound projections (callbacks)

| Projection | BPP → BAP | Built from |
|---|---|---|
| `projectOnSelect(order)` | `/on_select` | Order's Quote |
| `projectOnInit(order)` | `/on_init` | Order's populated Contract (with `contact_snapshot`) |
| `projectOnConfirm(order)` | `/on_confirm` | Confirmed Order |
| `projectOnStatus(order)` | `/on_status` | Current Order state |
| `projectOnCancel(order)` | `/on_cancel` | Cancelled Order |

Each projection does:

1. **Build wire payload** via `mapping-registry/` (e.g., `Order → Contract`).
2. **Enrich with protocol metadata** (context block, signatures).
3. **Sign** (`protocol/signing.ts`).
4. **Dispatch to BAP callback URL** with retry on transport failure.

### CDS publishing (event-driven, via ONIX)

The catalog publisher subscribes to domain events and POSTs `/catalog/publish` payloads to ONIX, which signs and forwards to CDS. The catalog publisher subscribes to domain events that affect what BAPs should see:

| Subscribed event | Behavior |
|---|---|
| `tenancy.store_status_changed` | Re-project store's catalogs; publish to CDS |
| `tenancy.store_republish_requested` | Manual republish for one store |
| `tenancy.org_republish_all_requested` | Fan out: republish all stores in the Org |
| `catalog.product_created`, `_updated`, `_published`, `_archived`, `_restored`, `_media_updated` | Re-project affected store's catalogs |
| `catalog.product_variant_*` | Same |
| `catalog.product_category_assigned`, `_unassigned` | Same |
| `catalog.store_catalog_created`, `_renamed`, `_deleted`, `product_included_in_catalog`, `_removed_from_catalog` | Re-project store's catalogs |

The publisher is **idempotent** (re-projection from current state is always safe).

## Ports declared

The Bridge declares **external** ports for protocol-side dependencies (significantly slimmed after [ADR-0022](../../decisions/0022-onix-protocol-gateway.md)):

| Port | Purpose | Implementation |
|---|---|---|
| `ONIXClientPort` | POST full Beckn JSON envelopes to ONIX (outbound callbacks, CDS publish, etc.) | `platform-infra/beckn-network/onix-client/` adapter |
| `IONErrorRegistryPort` | Load + look up codes in `ion-specs/errors/registry.json` | `platform-infra/beckn-network/ion-error-registry-loader/` adapter |

Optional / defensive (depends on N1 + N2 resolution per [ADR-0022 §10](../../decisions/0022-onix-protocol-gateway.md#open-follow-ups)):

| Port | Purpose | Implementation |
|---|---|---|
| `BAPKeyResolverPort` | Resolve BAP public key for inbound re-verification | If N2 = (a): an in-house BAP-key-registry-client adapter. If N2 = (b): a pass-through that reads ONIX-forwarded headers. |
| `BPPSigningKeyPort` | (Only if N1 = (a)) sign CounterSignatures on Ack/Nack responses | Local signing key adapter |

**Removed after ADR-0022**: `BecknSigningKeyPort` (ONIX signs), `BecknRegistryClientPort` (ONIX handles registry), `BecknNetworkClientPort` direct-BAP variant (ONIX forwards), `CDSClientPort` (ONIX forwards), `IonSpecsValidatorPort` (ONIX validates at the door).

**Provides** to other code: nothing. The Bridge is consumed only by HTTP requests from ONIX (forwarded BAP traffic) and by domain-event subscribers (catalog publish, manual republish).

The Bridge **calls** every context's Application-Layer use cases as needed — no direct repository access ever.

## Migration sketch

`migrations/0008__bridge.sql`:

```sql
-- Protocol-boundary idempotency: dedup inbound by (transaction_id, message_id)
CREATE TABLE bridge_inbox (
  transaction_id text NOT NULL,
  message_id text NOT NULL,
  protocol_version text NOT NULL,
  message_type text NOT NULL,                   -- 'select' | 'init' | 'confirm' | ...
  received_at timestamptz NOT NULL DEFAULT now(),
  ack_response jsonb NOT NULL,                  -- cached acknowledgement returned to BAP
  PRIMARY KEY (transaction_id, message_id)
);

-- Outbound queue: callbacks awaiting dispatch / retry
CREATE TABLE bridge_outbox (
  id text PRIMARY KEY,
  transaction_id text NOT NULL,                 -- correlation
  message_id text NOT NULL,                     -- new message_id for this callback
  bap_id text NOT NULL,
  bap_callback_url text NOT NULL,
  payload jsonb NOT NULL,
  state text NOT NULL DEFAULT 'pending',        -- pending | sent | failed | dead
  attempt_count int NOT NULL DEFAULT 0,
  last_attempt_at timestamptz,
  last_error text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_bridge_outbox_pending
  ON bridge_outbox (created_at) WHERE state = 'pending';
```

## Cross-context integration

| Direction | Detail |
|---|---|
| **Calls** | All contexts' Application-Layer use cases (Order primarily; Catalog read-side; Inventory `BulkGetAvailability`) |
| **Imports forbidden** | Any context's `domain/` or `infrastructure/` |
| **Subscribes to** | `tenancy.store_status_changed`, `tenancy.*_republish_*`, all `catalog.*` mutation events |
| **Events emitted** | None (the Bridge emits Beckn protocol messages, not domain events) |
| **Consumed by** | Only the network. No internal consumers. |

## Implementation order (within the Bridge)

1. **Resolve open follow-ups** from [ADR-0022 §10](../../decisions/0022-onix-protocol-gateway.md#open-follow-ups) — N1 (CounterSignature signing locus) and N2 (BAP key for re-verification). These affect which ports are needed.
2. **Protocol scaffolding** — `envelope`, `context-block`, `verification` (inbound re-verification only; per N2, may use ONIX-forwarded header or in-house registry client).
3. **`ion-error-registry.ts`** — load `ion-specs/errors/registry.json` at startup; expose lookup + reverse mapping.
4. **`onix-client/` adapter** — thin HTTPS POST client targeting `ONIX_ENDPOINT`. Parses ONIX failure responses (`{ errorCode, errorMessage }`); 5xx → retry signal, 4xx → fatal signal.
5. **`bridge_inbox` table** + `protocol/idempotency.ts` — dedup by `(transaction_id, message_id)`.
6. **`bridge_outbox` table** + dispatcher for outbound POSTs to ONIX (with retry on 5xx).
7. **`ack-builder.ts`** — Ack / AckNoCallback / Nack response construction with CounterSignature (per N1 resolution: either BPP-signed or ONIX-added).
8. **`mapping-registry/` skeleton** + `README.md` indexing entries.
9. **Inbound `/select`** — re-verify sig, validate (light), dedup, map → `Order.CreateQuote`, Ack/Nack.
10. **Outbound `/on_select`** — project Order's Quote → wire Contract → POST to ONIX.
11. **Correlation infrastructure** (`protocol/correlation.ts`) — match outbound callbacks to inbound transactions (`transaction_id` preserved by ONIX).
12. **Inbound `/init`** + **outbound `/on_init`**.
13. **Inbound `/confirm`** + **outbound `/on_confirm`**.
14. **Inbound `/status`** + **outbound `/on_status`**.
15. **Inbound `/cancel`** + **outbound `/on_cancel`**.
16. **Catalog publisher** — subscribe to events, project, POST to ONIX `/catalog/publish`. Wire-state mapping (Active → `isActive: true`; Paused / Suspended → `isActive: false`; Draft → not published).
17. **Multi-catalog projection** (`catalog-projection.ts` mapping entry) — Default + additional Catalogs per [§3.4.1 of handoff](../../handoff/03-beckn-integration.md).
18. **Locale resolution** (`mapping-registry/locale.ts`) — per-request `context.language` resolved via `LocalizedText.get`. No automatic translation.
19. **Error mapping** (`mapping-registry/errors.ts`) — every domain error type to an ION-XXXX code (registry-backed); unmappable → generic protocol error AND log mismatch.
20. **Manual republication handler** — `tenancy.store_republish_requested` and `org_republish_all_requested` subscribers.

## Test checklist (heaviest in the codebase)

Per [§7.7 of `07-testing.md`](../07-testing.md). All tests use **real ion-specs payloads**.

**Inbound parsing** (per message type × per supported protocol version):
- [ ] Valid payload → invokes the expected Application use case with expected inputs.
- [ ] Inbound signature **re-verified** at the Bridge (even though ONIX already verified) — for CounterSignature attestation per [ADR-0022 §6](../../decisions/0022-onix-protocol-gateway.md).
- [ ] Invalid re-verification → Nack with ION-1001 (signature failure).
- [ ] Duplicate by `(transaction_id, message_id)` → short-circuits; cached Ack returned; Application use case invoked exactly once.

**Outbound projection** (per callback type):
- [ ] Domain object → wire payload round-trips against `ion-specs` examples.
- [ ] Required protocol metadata present (full `context` block including `bpp_id` + `bpp_uri`). No `Authorization` header on POST to ONIX — ONIX adds it.
- [ ] Locale resolution: BAP-requested locale present → returned; absent → default-locale fallback.

**ONIX client** (`platform-infra/beckn-network/onix-client/`):
- [ ] POSTs full Beckn JSON envelope to `ONIX_ENDPOINT`.
- [ ] On 2xx response → outbox row marked `sent`.
- [ ] On 5xx response (including ION-9001) → outbox row remains `pending` with exponential-backoff retry.
- [ ] On 4xx response → outbox row marked `dead`; event emitted for ops review.
- [ ] Response body parsed as `{ errorCode: "ION-XXXX", errorMessage }` when non-2xx.

**ION error registry** (`protocol/ion-error-registry.ts`):
- [ ] Loads `ion-specs/errors/registry.json` at startup.
- [ ] `lookup("ION-9001")` returns the expected `{ http_status: 500, ... }` shape.
- [ ] Reverse mapping: every domain `TypedError` resolves to an ION-XXXX code, with unmappable cases falling through to a generic + logged mismatch.

**Ack / Nack** (`protocol/ack-builder.ts`):
- [ ] Every inbound gets exactly one of Ack / AckNoCallback / Nack.
- [ ] CounterSignature present on all three (per N1 resolution).
- [ ] Nack carries the appropriate ION-XXXX code.

**Mapping registry** (round-trip per entry):
- [ ] `order-to-contract`: Confirmed Order → wire Contract with `status: ACTIVE`; Cancelled → `CANCELLED`; etc.
- [ ] `voucher-to-offer`: Voucher → wire Offer; round-trip.
- [ ] `errors`: every `TypedError` subclass in the domain has an ION-XXXX mapping (or falls through to generic with logged mismatch).
- [ ] `locale`: `LocalizedText` with multiple entries → correct entry returned per request locale.

**Correlation**:
- [ ] Outbound `/on_select` carries the matching `transaction_id` from the inbound `/select`.
- [ ] Cross-flow correlation: a `/cancel` for an order created earlier in the same transaction finds the right Order.
- [ ] `transaction_id` + `message_id` preserved through ONIX (ONIX is transparent).

**CDS publishing**:
- [ ] `tenancy.store_status_changed` to Active triggers a publish (POST to ONIX `/catalog/publish`) with `isActive: true`.
- [ ] `tenancy.store_status_changed` to Paused triggers a publish with `isActive: false`.
- [ ] `catalog.product_published` triggers a re-projection.
- [ ] Manual `store_republish_requested` triggers a re-projection.
- [ ] `org_republish_all_requested` fans out per store in the Org.
- [ ] Re-projection is idempotent (publishing the same state twice is safe).

**End-to-end** (stub ONIX + stub BAP — per [§7.8 of `07-testing.md`](../07-testing.md)):
- [ ] `/select → /on_select → /init → /on_init → /confirm → /on_confirm` happy path through stub ONIX.
- [ ] `/cancel` from Initiated → reservations released.
- [ ] `/cancel` from Confirmed → voucher reverted; payment Refunded.
- [ ] Quote TTL expiry → `/on_status` reflects Expired.
- [ ] ONIX returning 5xx (ION-9001) → outbox retries; eventual success.
- [ ] ONIX returning 4xx (e.g., ION-1001 signing failure) → outbox marks `dead`; event emitted.

## Gotchas

- **Beckn vocabulary stays in the Bridge.** Never in domain, never in Application, never in admin-api. The lint rule (per [§2.8 of `02-repo-layout.md`](../02-repo-layout.md)) enforces this — but watch in code review too. If you see `descriptor`, `provider`, `resource`, `offer`, `contract`, `commitment`, `consideration`, `performance`, `context`, `intent` anywhere outside `bridge/`, that's leakage.
- **The Bridge no longer signs outbound** ([ADR-0022](../../decisions/0022-onix-protocol-gateway.md)). ONIX adds the `Authorization` header. The BPP POSTs unsigned envelopes. **Do not** add an `Authorization` header to outbound POSTs — ONIX may reject or behave incorrectly.
- **Inbound signature re-verification is mandatory** even though ONIX verifies first. The CounterSignature in the BPP's Ack attests *the BPP* authenticated. Without re-verification, the attestation is implicit-via-ONIX and breaks the protocol contract ([ADR-0022 §6](../../decisions/0022-onix-protocol-gateway.md)).
- **Beckn is async, callback-driven.** Acknowledge inbound requests immediately; deliver substantive responses via callbacks. Correlation by `transaction_id` is the Bridge's problem, not the Application Layer's. ONIX preserves `transaction_id` / `message_id` end-to-end.
- **The Bridge keeps protocol-level idempotency** even though ONIX dedups at the network door (ION-1004, 30-minute window). Defense in depth. Domain `Idempotency-Key` middleware doesn't replace it.
- **Errors translate via the ION-XXXX registry.** Domain errors → ION-XXXX codes for Nack / outbound. ONIX failures → BPP retry-or-fatal decisions based on HTTP status class (5xx retry, 4xx fatal). The Bridge loads `ion-specs/errors/registry.json` at startup — don't hand-code mappings.
- **Unmappable domain errors → generic protocol error AND log the mismatch.** Silent loss of information is forbidden ([§3.11 of handoff](../../handoff/03-beckn-integration.md)).
- **Multi-catalog projection has Bridge-only mapping** ([§3.4.1 of handoff](../../handoff/03-beckn-integration.md)). The domain has `Catalog` entities; the wire has whatever shape the registry decides. Don't push that decision into Catalog.
- **CDS is mandated**; BPP does NOT field `/discover` directly ([ADR-0017](../../decisions/0017-order-and-fulfillment.md)). Discovery is BAP → CDS → BPP transactional only — and the transactional traffic goes via ONIX.
- **Registry lifecycle is ONIX's concern**, not the BPP's. The BPP no longer holds registry credentials. Key rotation is an ONIX vendor operation (see [§9.5 of `09-runbooks.md`](../09-runbooks.md)).
- **`bpp-uri` is the ONIX network-facing URL**, not the BPP's HTTP endpoint. The BPP sets this in outbound `context.bpp_uri`; ONIX is the BAP-visible host.
- **Wire-state mapping lives in `mapping-registry/`**, not in the domain:
  - Store status `Active` → Catalog `isActive: true`.
  - Store status `Paused` / `Suspended` → Catalog `isActive: false`.
  - Store status `Draft` → not published.
  - Order status `Created` / `Initiated` → Contract `DRAFT`.
  - Order status `Confirmed` → Contract `ACTIVE`.
  - Order status `Fulfilled` → Contract `COMPLETE`.
  - Order status `Cancelled` / `Expired` → Contract `CANCELLED`.
- **Versioning lives in `protocol/versions/`.** Per-version handlers + mappings; multiple versions can coexist. ONIX is **transparent on version** — it does not version-translate. BPP targets Beckn v2.0.0 directly.
- **Outbound dispatch can fail.** The `bridge_outbox` table + dispatcher handles retry to ONIX. Failed POSTs after N attempts go to `state: 'dead'` for operator review. ION-9001 (ION internal error) and other 5xx → retry. 4xx → fatal.
- **The Bridge does NOT emit domain events.** Anyone wanting "the Bridge sent a callback" as an audit signal should check `bridge_outbox` or rely on the domain event upstream (e.g., `order.confirmed`) that triggered the callback.
- **ONIX availability is a SPOF.** If ONIX is down, the BPP is off-network. Mitigated by per-BPP deployment, zero-downtime ONIX restarts, and outbox retry. See [§9.5 of `09-runbooks.md`](../09-runbooks.md) for triage.
- **Open follow-ups from [ADR-0022 §10](../../decisions/0022-onix-protocol-gateway.md#open-follow-ups)** (N1 CounterSignature signing locus, N2 BAP key for re-verification) must be resolved before Phase 6 implementation lands. They shape which ports are needed.
