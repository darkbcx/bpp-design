# 6.4 Inventory — playbook

How to implement the Inventory context. Small but concurrency-sensitive — it owns *is the item purchasable right now* (stock counts, reservations, owner-controlled availability) and is the choke point for Order confirmation.

> **Read first**: [handoff §4.4 Inventory](../../handoff/04-bounded-contexts/4.4-inventory.md), [ADR-0006](../../decisions/0006-inventory-model.md).

## At a glance

| Aspect | Detail |
|---|---|
| Phase landed | [Phase 4](../05-phases.md) — Inventory + Promotion (parallel) |
| Owns | `StockLevel`, `Reservation`, stock-movement events |
| Anchors to | `Product` (Flat mode) or `ProductVariant` (Matrix mode) — by ID, no join |
| External systems | None directly |
| Cross-context users | Order (reserves at `/init`, converts at `/confirm`, releases on cancel), Bridge (availability lookup for CDS publishing) |
| First migration | `0005__inventory.sql` |

## Entities

### `StockLevel`

| Field | Notes |
|---|---|
| `id` | Internal opaque |
| `store_id` | Cross-context ref |
| `inventory_item_ref` | `{ type: 'product' \| 'variant', id }` — opaque pointer to Catalog |
| `stock_count` | Integer ≥ 0; physical units on hand |
| `purchasable` | Boolean; owner-controlled; default `true` |
| `status` | `'active' \| 'inactive'` (cascaded from Catalog item lifecycle) |
| `created_at`, `updated_at` | |

**Invariants:**
- `stock_count ≥ 0` always.
- One `StockLevel` per `inventory_item_ref` per store.
- `status = 'inactive'` rejects new reservations.

### `Reservation`

| Field | Notes |
|---|---|
| `id` | |
| `stock_level_id` | |
| `quantity` | Integer ≥ 1 |
| `held_by_ref` | Opaque — typically Order's `transaction_id` or internal cart ID |
| `expires_at` | When the hold automatically releases if not converted |
| `state` | `'active' \| 'converted' \| 'released'` |
| `created_at`, `state_changed_at` | |

**Lifecycle:**
- `(new) → active` at Reserve.
- `active → converted` at ConvertReservation (decrements `stock_count` atomically).
- `active → released` at ReleaseReservation OR at expiry sweep.
- No other transitions.

### Effective availability (computed at read time — no cached projection)

```
active_reservations = sum(Reservation.quantity)
  where stock_level_id = X AND state = 'active' AND expires_at > now

available_quantity = max(0, stock_count - active_reservations) if purchasable AND status = 'active'
                     else 0

available_for_purchase = available_quantity > 0
```

Calculated in `domain/services/availability-calculator.ts`.

## Use cases

| # | Use case | Caller | Capability |
|---|---|---|---|
| 1 | `AdjustStock(item, delta, reason)` | Store Admin via HTTP | `inventory.adjust` — emits `stock.received` (delta > 0) or `stock.corrected` (delta < 0 or `reason` set) |
| 2 | `SetPurchasable(item, value)` | Store Admin | `inventory.set_purchasable` — emits `purchasable.toggled` |
| 3 | `Reserve(item, qty, held_by_ref)` | Order context (cross-context call) | (none — caller already authorized at Order's boundary) |
| 4 | `ConvertReservation(reservation_id)` | Order context | (none — same) |
| 5 | `ReleaseReservation(reservation_id)` | Order context OR `expire-reservations` job | (none) |
| 6 | `GetAvailability(item)` | Admin UI / Bridge | `inventory.read` (or open for Bridge) |
| 7 | `BulkGetAvailability([items])` | Bridge | (open for Bridge) |

### Use case envelope highlights

- **`Reserve` is the concurrency-critical path.** Use `SELECT ... FOR UPDATE` (or your DB's equivalent) on the `StockLevel` row inside the transaction, then check available capacity, then insert `Reservation`. The use-case envelope's transaction wraps this. See [§7.10 of `07-testing.md`](../07-testing.md) for the concurrency test.
- **`ConvertReservation` decrements `stock_count` atomically** with marking the Reservation `converted`. Same transaction.
- **`ReleaseReservation` is idempotent**. Releasing an already-released reservation is a no-op.
- **`AdjustStock` with `delta < 0` and no reason is rejected.** Owner must classify the adjustment.
- **`SetPurchasable(item, false)` doesn't release existing reservations.** It just gates new ones.

## Events emitted

| Event | Category | Trigger |
|---|---|---|
| `inventory.stock_level_created` | business_state | StockLevel auto-created (subscribed to `catalog.product_created` / `product_variant_added`) |
| `inventory.stock_level_inactivated` | business_state | Catalog item archived |
| `inventory.stock_received` | inventory | Owner manual receipt (delta > 0) |
| `inventory.stock_sold` | inventory | `ConvertReservation` decrement |
| `inventory.stock_returned` | inventory | Reserved for future Returns flow ([§7.2.6 of handoff](../../handoff/07-open-issues.md)); not emitted in v1 |
| `inventory.stock_corrected` | inventory | Manual adjustment with reason |
| `inventory.stock_reserved` | inventory | `Reserve` succeeded |
| `inventory.stock_released` | inventory | `ReleaseReservation` (incl. expiry sweep) |
| `inventory.purchasable_toggled` | inventory | `SetPurchasable` |

`inventory` category has a ~3-year retention default per [§4.7 of handoff](../../handoff/04-bounded-contexts/4.7-audit.md).

## Events subscribed

| Event | Handler | Behavior |
|---|---|---|
| `catalog.product_created` | `on-product-created` | If `mode='flat'`, auto-create StockLevel (count=0, purchasable=true, active). Skip for `mode='matrix'`. |
| `catalog.product_variant_added` | `on-product-variant-added` | Auto-create StockLevel per variant. |
| `catalog.product_archived` | `on-product-archived` | Mark all StockLevels for the product `inactive`. |
| `catalog.product_restored` | `on-product-restored` | Mark all StockLevels `active`. |
| `catalog.product_variant_removed` | `on-product-variant-removed` | Mark the variant's StockLevel `inactive`. |

All subscribers must be **idempotent** (inbox dedup handles double-delivery, but logic must not duplicate work either).

## Migration sketch

`migrations/0005__inventory.sql`:

```sql
CREATE TYPE stock_level_status AS ENUM ('active', 'inactive');
CREATE TYPE reservation_state AS ENUM ('active', 'converted', 'released');

CREATE TABLE stock_levels (
  id text PRIMARY KEY,
  store_id text NOT NULL,                       -- cross-context ref
  inventory_item_type text NOT NULL,            -- 'product' | 'variant'
  inventory_item_id text NOT NULL,              -- cross-context ref to Catalog
  stock_count int NOT NULL DEFAULT 0 CHECK (stock_count >= 0),
  purchasable boolean NOT NULL DEFAULT true,
  status stock_level_status NOT NULL DEFAULT 'active',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (store_id, inventory_item_type, inventory_item_id)
);

CREATE TABLE reservations (
  id text PRIMARY KEY,
  stock_level_id text NOT NULL REFERENCES stock_levels(id),
  quantity int NOT NULL CHECK (quantity > 0),
  held_by_ref text NOT NULL,
  expires_at timestamptz NOT NULL,
  state reservation_state NOT NULL DEFAULT 'active',
  created_at timestamptz NOT NULL DEFAULT now(),
  state_changed_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_reservations_stock_level_active
  ON reservations (stock_level_id) WHERE state = 'active';
CREATE INDEX idx_reservations_expires_at_active
  ON reservations (expires_at) WHERE state = 'active';
```

## Cross-context integration

| Direction | Detail |
|---|---|
| **Provides** | `InventoryReservationPort` (Order); `InventoryAvailabilityReadPort` (Bridge) |
| **Consumes** | `AuthorizationPort` (Tenancy) — for owner-facing use cases only; cross-context calls from Order are pre-authorized |
| **Events consumed by** | Audit (broadly); Bridge (via Catalog republication — Bridge re-queries availability when projecting) |
| **Subscribes to** | Catalog product/variant lifecycle events (auto-StockLevel management) |

## Implementation order (within this context)

1. **`StockLevel`** entity + repository + `on-product-created` / `on-product-variant-added` subscribers (lights up auto-creation as soon as Catalog Phase 3 emits).
2. **`AdjustStock`** + **`SetPurchasable`** + their HTTP routes for Admin UI.
3. **`AvailabilityCalculator`** service + **`GetAvailability`** + **`BulkGetAvailability`**.
4. **`Reservation`** entity + repository.
5. **`Reserve`** use case (with `FOR UPDATE` locking) — write the concurrency test FIRST.
6. **`ConvertReservation`** — atomic decrement.
7. **`ReleaseReservation`** — idempotent.
8. **`InventoryReservationPortAdapter`** for Order.
9. **`expire-reservations` job** + scheduled trigger.
10. **`on-product-archived` / `on-product-restored` / `on-product-variant-removed`** subscribers — cascade `status`.

## Test checklist

**Domain tests**:
- [ ] `AvailabilityCalculator` correctness across all four flag combinations (purchasable × status).
- [ ] `StockLevel.stock_count` cannot go negative (invariant check at construction).
- [ ] `Reservation` state machine — illegal transitions throw.

**Application tests**:
- [ ] `Reserve` succeeds when sufficient effective availability; rejects with `InsufficientStockError` when not.
- [ ] `Reserve` rejects when `StockLevel.status = 'inactive'`.
- [ ] `Reserve` rejects when `purchasable = false`.
- [ ] `ConvertReservation` decrements `stock_count` AND marks reservation `converted` AND emits `stock.sold` — all atomically.
- [ ] `ReleaseReservation` is idempotent.
- [ ] `AdjustStock(delta < 0, no reason)` rejected.
- [ ] `on-product-created` subscriber auto-creates a StockLevel for Flat mode; skips for Matrix.
- [ ] `on-product-variant-added` subscriber auto-creates per variant.
- [ ] All subscribers are idempotent under replay.

**Infrastructure tests**:
- [ ] Round-trip StockLevel + Reservation through repos.
- [ ] `CHECK (stock_count >= 0)` enforced by DB.

**Concurrency tests** (required per [§7.10 of `07-testing.md`](../07-testing.md)):
- [ ] Concurrent `Reserve(item, 1)` calls on `StockLevel{stock_count: 1}`: exactly one succeeds.
- [ ] Concurrent `Reserve` + `ConvertReservation` on the same StockLevel produce correct final `stock_count`.
- [ ] `expire-reservations` job operating concurrently with `Reserve` doesn't drop stock.

## Gotchas

- **`stock_count` only changes via Reservation conversion, manual `Corrected`, or `Received`.** Direct stock writes outside these paths are forbidden. Make this enforceable by code review or, better, by lint / DB-level checks.
- **Effective availability is read-time computation.** No cached availability column. If you find yourself adding one, you've hit a scale problem worth a new ADR.
- **`SELECT ... FOR UPDATE` is mandatory for `Reserve`.** Without it, concurrent Reserves can oversell. Test this with the concurrency test before declaring `Reserve` done.
- **Single-location only in v1.** No multi-warehouse. If business asks for it, that's [§7.2.4 of handoff](../../handoff/07-open-issues.md) — explicit deferral.
- **No backorders.** Cannot sell beyond `stock_count`. `purchasable=true` is necessary but not sufficient for availability.
- **Inactivating a Catalog item doesn't release existing reservations.** It just prevents new ones. Order's cancel paths release explicitly.
- **`held_by_ref` is opaque to Inventory.** The caller (Order) interprets it. Don't model it as `transaction_id` or `cart_id` — keep it as a string.
- **Subscriber idempotency is critical.** Inbox dedup handles double-delivery from the bus, but if Catalog's event for `product_created` arrives twice somehow, the subscriber must produce the same StockLevel each time — don't accidentally create duplicates.
- **`AdjustStock` is the only manual stock operation in v1.** Bulk import / supplier integration / automated receiving are deferred ([§7.2.4 of handoff](../../handoff/07-open-issues.md)).
- **Reservation timeout is operational config**, not architectural. Default leans 15 minutes (matching Quote TTL); make it tunable.
