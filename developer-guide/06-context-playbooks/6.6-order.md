# 6.6 Order & Fulfillment — playbook

How to implement the Order context. This is the integration heavyweight — it orchestrates Catalog (snapshots), Inventory (Reservations), and Promotion (vouchers) into end-to-end commerce flows. The Beckn Bridge is the **sole external entry point** ([ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)); the Admin UI only handles fulfillment-side actions.

> **Read first**: [handoff §4.6 Order & Fulfillment](../../handoff/04-bounded-contexts/4.6-order.md), [`design/order.md`](../../design/order.md), [ADR-0017](../../decisions/0017-order-and-fulfillment.md), [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md), [§5.3 of handoff](../../handoff/05-cross-cutting.md) (orchestration with compensation).

## Entities

### `Order`

| Field | Notes |
|---|---|
| `id` | Internal opaque |
| `store_id` | Cross-context ref |
| `status` | `'created' \| 'initiated' \| 'confirmed' \| 'fulfilled' \| 'cancelled' \| 'expired'` |
| `quote` | Embedded; immutable after `Created` |
| `buyer` | Embedded: `{ bap_id, transaction_id, contact_snapshot? }` (Beckn-typed per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)) |
| `reservation_ids` | Array; populated at `Initiated` |
| `voucher_usage_id` | Nullable; set at `Confirmed` if voucher applied |
| `payment_status` | `'pending' \| 'authorized' \| 'captured' \| 'refunded' \| 'failed'` — driven by external signals |
| `payment_external_ref` | Nullable; BAP-supplied or future gateway ref |
| `fulfillment_status` | `'pending' \| 'preparing' \| 'shipped' \| 'delivered'` |
| `fulfillment_note` | Optional free-text |
| `cancel_reason` | Optional |
| Timestamps | created_at, last_status_change_at, completed_at |

**Lifecycle (status):**

```
       [new] → Created → Initiated → Confirmed → Fulfilled
                 │           │           │
                 │           └────┬──────┘
                 │                ↓
                 │             Cancelled
                 ↓
              Expired
```

- `Created → Expired`: Quote TTL passed without `Initiate`.
- `Initiated → Expired`: Quote TTL passed without `Confirm`. Reservations released.
- `Confirmed → Cancelled` (pre-fulfillment only): voucher reverted; payment marked Refunded.
- `Confirmed → Fulfilled`: when `fulfillment_status` reaches `Delivered`.
- No deletion (consistent with [§5.5 of handoff](../../handoff/05-cross-cutting.md)).

**Audit retention bucket: `financial` (~7 years).**

### `Quote` (embedded; immutable after `Created`)

| Field | Notes |
|---|---|
| `line_items` | Array of LineItem with captured snapshots |
| `voucher_applied` | Nullable: `{ voucher_id, code, discount_type, discount_value, discount_amount }` |
| `totals` | `{ subtotal, tax_total, discount_total, grand_total }` — all `Money` |
| `currency` | From Store |
| `valid_until` | TTL anchor; default 15 min (operational) |
| `created_at` | |

### `LineItem` (embedded; captured snapshots — do not auto-refresh)

| Field | Notes |
|---|---|
| `item_ref` | `{ type, id }` — Product (Flat) or Variant (Matrix) |
| `quantity` | Integer ≥ 1 |
| `captured_name`, `captured_description` | `LocalizedText` snapshots |
| `captured_base_price`, `captured_tax_rate` | `Money` / decimal at quote time |
| `captured_tax_amount`, `captured_published_price` | Derived from base × rate at quote time |
| `line_subtotal` | `Money` = `captured_published_price × quantity` |

**Why captured snapshots:** if Catalog prices or `LocalizedText` change after the Quote is created, the Order remains as quoted. Receipt stability is non-negotiable.

### `Buyer`

```ts
buyer = {
  bap_id: string;
  transaction_id: string;
  contact_snapshot?: {              // null at Created; populated at Initiated
    name: LocalizedText;
    email: string;                  // PII — tagged
    phone: string;                  // PII — tagged
    address: ShippingAddress;       // PII — tagged
  };
}
```

Per [ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md): there is no `user_id` field. Buyers are Beckn-typed only.

## Use cases

### Bridge-driven (the sole external entry)

| # | Use case | Bridge route | Notes |
|---|---|---|---|
| 1 | `CreateQuote(store_id, items, voucher_code?, beckn_buyer_ref)` → `Order` | `/select` | Creates Order in `Created` with embedded Quote. Calls Catalog for snapshots; calls Promotion to validate voucher (no record yet). No Inventory reservation yet. |
| 2 | `Initiate(order_id, contact_snapshot)` → `Order` | `/init` | Orchestration: reserves Inventory for each line item; re-validates voucher; persists `reservation_ids` + `contact_snapshot`. Compensates by releasing reservations on failure. |
| 3 | `Confirm(order_id)` → `Order` | `/confirm` | Orchestration: converts all reservations atomically; records voucher usage if applied. |
| 4 | `Cancel(order_id, reason, by_actor)` → `Order` | `/cancel` (or admin) | Branches: from `Initiated` releases reservations; from `Confirmed` reverts voucher + marks payment `Refunded`. |
| 5 | `GetStatus(order_id)` → `Order` | `/status` | Read-only. |
| 6 | `UpdatePaymentStatus(order_id, status, external_ref)` | (Bridge or future gateway webhook) | External signal handler. Validates allowed transitions. Emits `payment_status_changed`. |

### Fulfillment (Store Admin)

| # | Use case | Capability | Notes |
|---|---|---|---|
| 7 | `MarkPreparing(order_id, by_actor)` | `order.fulfillment.update` | `fulfillment_status: Pending → Preparing`. Order status stays `Confirmed`. |
| 8 | `MarkShipped(order_id, by_actor, fulfillment_note?)` | `order.fulfillment.update` | `Preparing → Shipped`. |
| 9 | `MarkFulfilled(order_id, by_actor)` | `order.fulfillment.update` | `Shipped → Delivered`. Order status transitions `Confirmed → Fulfilled`. Emits `order.fulfilled`. |

### Read-side (Admin UI)

| # | Use case | Capability |
|---|---|---|
| 10 | `ListOrdersForStore(store_id, filter, acting_user)` | `order.read` |

### Use case envelope highlights

- **`CreateQuote` doesn't reserve stock.** It only validates availability. Reservations come at `Initiate`.
- **`Initiate` is the first orchestration.** Pseudocode:
  ```
  load Order; assert status == Created; assert TTL not expired
  for each line: reservation = Inventory.Reserve(item, qty, held_by = order_id)
    on failure: for each reservation already made: Inventory.ReleaseReservation; raise
  if voucher: Promotion.ValidateVoucher(...)
    on failure: release all reservations; raise
  persist: reservation_ids, contact_snapshot; status = Initiated
  emit: order.initiated
  ```
- **`Confirm` is the second orchestration.** Pseudocode:
  ```
  load Order; assert status == Initiated; assert TTL not expired
  for each reservation_id: Inventory.ConvertReservation(...)
  if voucher: Promotion.RecordVoucherUsage(...); persist voucher_usage_id
  status = Confirmed; persist; emit: order.confirmed
  ```
- **`Cancel` branches by current state.** Pseudocode:
  ```
  load Order; assert status in {Created, Initiated, Confirmed}
  match status:
    Initiated:  for each reservation_id: Inventory.ReleaseReservation(...)
    Confirmed:  if voucher_usage_id: Promotion.RevertVoucherUsage(...)
                if payment_status == Captured: set Refunded; emit payment_status_changed
  status = Cancelled; persist; emit: order.cancelled
  ```
- **Compensation is hand-coded.** No Saga framework in v1 ([§5.3.3 of handoff](../../handoff/05-cross-cutting.md)).
- **The use-case envelope owns the transaction.** All sub-context calls happen within Order's transaction; the cross-context ports accept the tx client (per [§4.10](../04-conventions.md)).
- **Bridge-driven use cases bypass the capability check** at Order's boundary because the Bridge is a pre-authorized principal. The Bridge's adapter passes a synthetic actor.

## Migration sketch

`migrations/0007__order.sql`:

```sql
CREATE TYPE order_status AS ENUM ('created', 'initiated', 'confirmed', 'fulfilled', 'cancelled', 'expired');
CREATE TYPE payment_status AS ENUM ('pending', 'authorized', 'captured', 'refunded', 'failed');
CREATE TYPE fulfillment_status AS ENUM ('pending', 'preparing', 'shipped', 'delivered');

CREATE TABLE orders (
  id text PRIMARY KEY,
  store_id text NOT NULL,                       -- cross-context ref

  status order_status NOT NULL DEFAULT 'created',
  payment_status payment_status NOT NULL DEFAULT 'pending',
  fulfillment_status fulfillment_status NOT NULL DEFAULT 'pending',

  -- embedded Quote + LineItems as JSONB (atomically loaded with Order)
  quote jsonb NOT NULL,                         -- { line_items, voucher_applied, totals, currency, valid_until }

  -- Buyer (Beckn-typed)
  bap_id text NOT NULL,
  transaction_id text NOT NULL,
  contact_snapshot jsonb,                       -- nullable until Initiated; PII fields tagged in catalog

  -- Cross-references populated as the Order progresses
  reservation_ids text[] NOT NULL DEFAULT ARRAY[]::text[],   -- cross-context refs to Inventory
  voucher_usage_id text,                                       -- cross-context ref to Promotion

  payment_external_ref text,
  fulfillment_note text,
  cancel_reason text,

  created_at timestamptz NOT NULL DEFAULT now(),
  last_status_change_at timestamptz NOT NULL DEFAULT now(),
  completed_at timestamptz,                     -- set on Fulfilled / Cancelled / Expired

  UNIQUE (bap_id, transaction_id)                -- protocol-level uniqueness per BAP transaction
);

CREATE INDEX idx_orders_store_status ON orders (store_id, status);
CREATE INDEX idx_orders_quote_valid_until
  ON orders ((quote->>'valid_until')) WHERE status IN ('created', 'initiated');
```

**Note:** the embedded JSONB approach keeps the Quote atomic and immutable — no risk of partial updates across normalized line-item rows. Trade-off: querying inside `quote` requires JSONB operators. For v1 traffic, fine.

## Implementation order (within this context)

1. **`Order`** entity + `OrderStatus` state machine + repository (without orchestrations yet — just empty Order creation).
2. **`Quote`** + **`LineItem`** value objects + `TotalsCalculator` service.
3. **External port declarations** (`CatalogReadPort`, `InventoryReservationPort`, `PromotionVoucherPort`) — interfaces only. Catalog / Inventory / Promotion implement the adapters in their own infra.
4. **`CreateQuote`** — calls Catalog for snapshots; calls Promotion for validation (no record). No reservations yet.
5. **`Initiate`** with orchestration + compensation. Test this thoroughly.
6. **`Confirm`** with orchestration.
7. **`Cancel`** with branching by current status.
8. **`GetStatus`** (read-only).
9. **`UpdatePaymentStatus`** (external signal handler).
10. **`MarkPreparing` / `MarkShipped` / `MarkFulfilled`** (admin fulfillment progression).
11. **`expire-quotes` job** — background sweep; releases reservations for expired Initiated orders.
12. **Admin HTTP routes** (list, detail, cancel, fulfillment actions).
13. **`ListOrdersForStore`** with capability-gated read.

## Test checklist

**Domain tests**:
- [ ] `Order` status state machine — every legal transition; every illegal one throws `OrderStatusTransitionNotAllowedError`.
- [ ] `Fulfillment` state machine — same.
- [ ] `Quote.valid_until` TTL check rejects `Confirm` past TTL.
- [ ] `LineItem` snapshot captures don't mutate after creation.
- [ ] `TotalsCalculator` rounding correctness.
- [ ] State-machine property tests (per [§7.9 of `07-testing.md`](../07-testing.md)).

**Application tests**:
- [ ] `CreateQuote` happy path: Order in `Created`, line items have captured snapshots; voucher validated but not recorded.
- [ ] `CreateQuote` rejected when product not found / inactive.
- [ ] `Initiate` happy path: reserves inventory, captures contact, persists `reservation_ids`, status `Initiated`, event emitted.
- [ ] `Initiate` compensation: voucher validation failure releases all already-made reservations.
- [ ] `Initiate` compensation: insufficient stock on line 3 releases lines 1 and 2.
- [ ] `Confirm` happy path: reservations converted, voucher recorded, status `Confirmed`.
- [ ] `Confirm` rejected when status ≠ `Initiated`.
- [ ] `Confirm` rejected when TTL expired.
- [ ] `Cancel` from `Initiated` releases reservations.
- [ ] `Cancel` from `Confirmed` reverts voucher + sets payment `Refunded`.
- [ ] `Cancel` from `Created` is a simple status change.
- [ ] `MarkFulfilled` transitions Order status to `Fulfilled` AND emits `order.fulfilled`.
- [ ] `expire-quotes` job releases reservations for expired Initiated orders.

**Infrastructure tests**:
- [ ] Round-trip Order with embedded Quote through repo.
- [ ] `UNIQUE (bap_id, transaction_id)` enforced.
- [ ] JSONB `quote` field round-trips with type fidelity (Money amounts as bigint).

**Concurrency tests** (per [§7.10 of `07-testing.md`](../07-testing.md)):
- [ ] Concurrent `Cancel` and `Confirm` on the same Order: at most one succeeds.

## Gotchas

- **The Bridge is the only external entry.** No first-party Order placement use case ([ADR-0021](../../decisions/0021-pure-bpp-no-storefront.md)). Don't expose `CreateQuote` / `Initiate` / `Confirm` on the admin-api surface.
- **Quote snapshots are immutable** once Created. Don't add "refresh quote" logic — that's a deliberate design choice for receipt stability.
- **Quote has a TTL** (default 15 min; operational). After expiry, the Order moves to `Expired`; reservations release if held. The TTL is enforced both at use-case entry AND by the background sweep.
- **Stock is NOT returned on cancel-from-Confirmed** in v1. The Returns flow is deferred ([§7.2.6 of handoff](../../handoff/07-open-issues.md)). The voucher IS reverted; payment IS marked Refunded (external).
- **Cancellation is pre-fulfillment only**. Once `fulfillment_status = Delivered`, no Cancel use case applies. Post-fulfillment refund/return is deferred.
- **No Saga framework**. Multi-context orchestrations use hand-coded compensation ([§5.3.3 of handoff](../../handoff/05-cross-cutting.md)). Each external call has a paired release/revert.
- **Payment is external**. BPP doesn't store card data or capture payments. `payment_status` updates come from outside (BAP signals via Bridge, or future gateway webhooks). Don't bake payment flow assumptions into Order.
- **Self-fulfilled by stores**. No logistics provider integration in v1. `fulfillment_status` advances by store-admin actions ([§7.2.6 of handoff](../../handoff/07-open-issues.md)).
- **`buyer.contact_snapshot` is PII**. Tag every field in `design/pii.md`. Scrub-in-place on right-to-erasure.
- **No partial cancellation** in v1 (can't cancel some line items, keep others). Order is one-shot.
- **`UNIQUE (bap_id, transaction_id)`** is the protocol-level idempotency anchor. The Bridge's idempotency dedup is upstream; this is the last-line guarantee at the data layer.
- **`reservation_ids` and `voucher_usage_id` are cross-context refs**, not foreign-keyed. Inventory's reservation could be Released by the expiry sweep — Order must tolerate stale references on read (treat as no-op when cancelling).
- **The orchestrations should be unit-testable** without a real DB — port fakes for Inventory / Promotion / Catalog. The hardest part to get right is compensation; write those tests first.
